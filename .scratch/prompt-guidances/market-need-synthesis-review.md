## §ชน — สองข้อที่ต้องให้คนตัดสิน

### ชน-1 · กฎข้อ 2 กลับคำตัดสินที่ผ่านมาแล้ว 2 commit

**ของเดิมตั้งใจให้ opening อิสระ** `summarize_need.py:99-101` เสนอ 4 แบบ
(`ต้องการ...` / `ต้องการบัณฑิตที่...` / `ต้องการหลักสูตรที่...` / `บัณฑิตต้องมี...`)
มาจาก `a5823b9` (ถอด opening บังคับ `ตลาดแรงงานต้องการ`) แล้ว `e09b2d6` ตามไปแก้ prompt
ปลายน้ำ 3 ตัวที่ยังเขียนโดยสมมติว่า Need เปิดด้วยวลีนั้น — commit message บอกเองว่าการ
แยก Need จาก PLO ด้วย "เสียงตลาด vs เสียงผู้เรียน" ใช้ไม่ได้อีกแล้ว จึงเปลี่ยนเส้นแบ่งเป็น
**ข้อกำหนด vs ผลลัพธ์**

**guidance ห้าม `สามารถ...ได้` แบบเหมารวม** ซึ่งชนสามชั้น:

1. `บัณฑิตต้องมี...` ที่อนุญาตอยู่ ถูก **pin ด้วย test** —
   `test_summarize_prompt_offers_every_allowed_opening` parametrize ครบทั้ง 4 แบบ
2. **guidance ขัดกฎตัวเอง** — ✅ example ทุกตัวเขียน `ต้องการผู้ปฏิบัติงานที่**สามารถ**...`
   อ่านตามตัวอักษรแล้วตัวอย่างของมันเองตกกฎข้อ 2 → เจตนาจริงน่าจะห้าม *รูปผลลัพธ์การเรียนรู้*
   (`บัณฑิต/ผู้เรียน` เป็นประธาน) ไม่ใช่ห้ามคำว่า `สามารถ` ถ้อยคำต้องเขียนใหม่ให้ตรงเจตนา
3. **guidance เลื่อนประธานเป็น `ผู้ปฏิบัติงาน`** ทุกตัวอย่าง ขณะที่ role line ของเดิมคือ
   "ความต้องการที่มีต่อ**บัณฑิตและหลักสูตร**" (`:94`)

ข้อ 3 คือข้อที่ควรคิดหนักที่สุด: Need ไม่ได้มาจากนายจ้างอย่างเดียว มันมาจาก
`institutional_direction` (วิสัยทัศน์ของสถาบันเอง), `student`, `alumni` ด้วย —
และ `45692f2` ("stop asking every stakeholder what the labour market wants") คือ commit ที่
แก้ปัญหานี้ที่ชั้นสกัดมาแล้ว ชื่อไฟล์ guidance เอง ("Market Need Synthesis") และ role block
ที่ถามว่า "ตลาดแรงงานต้องการความสามารถอะไร" พา framing กลับไปทางเดิม

> **สิ่งที่ต้องตัดสิน**: จะรับ `ผู้ปฏิบัติงาน` เป็นประธานหลักไหม
> · **รับ** = Need อ่านเป็นเสียงตลาดชัดขึ้น แลกกับการกลับทิศ `a5823b9`/`e09b2d6`/`45692f2`
>   และต้องแก้ test 2 ตัว พร้อมเขียนเหตุผลใหม่ทับ docstring เดิม
> · **ไม่รับ** = เก็บ opening อิสระไว้ แล้วหยิบเฉพาะเจตนาของกฎข้อ 2 (ห้ามรูปผลลัพธ์การเรียนรู้)
>   ซึ่ง `:102-103` ทำอยู่แล้ว → กฎข้อ 2 กลายเป็น "ซ้ำของเดิม" ไม่ต้องแก้อะไร

### ชน-2 · กฎข้อ 11 ดันสวนทางกับกฎที่มีอยู่

กฎเดิมดัน **เข้าหา** ความเฉพาะเจาะจงอย่างเดียว: ต้องมี 3 ส่วน (`:104-105`), ห้ามคำกว้าง
(`:109-110`), ยาวไม่ต่ำกว่า 40 ตัวอักษร (`:114`) — ไม่มีกฎไหนบอกว่า "เฉพาะเกินไป" เป็นปัญหา

validator ฝั่งโค้ดทุกตัวและตรงกฎเดิมทุกข้อ แต่ guidance บอกว่าแคบเกินระดับหลักสูตร

ทั้งสองแรงมีเหตุผล (Need ที่กว้างเขียน PLO ไม่ได้ / Need ที่แคบเกินกลายเป็น CLO) แต่ prompt

> **สิ่งที่ต้องตัดสิน**: เส้นแบ่ง "ระดับหลักสูตร vs ภารกิจย่อย" คืออะไรที่เขียนเป็นกฎได้

> (`เอกสารวิชาชีพ` ✅ / `สัญญาซื้อขายสินค้า` ❌) — ยังเป็นข้อเสนอ ยังไม่ได้ทดสอบกับข้อมูลจริง

## §ไม่ฟรี — สองข้อที่ออกนอกขอบเขต "แก้ prompt"

### ไม่ฟรี-1 · `rationale_th` (กฎ 12 + checklist 10)

guidance สั่งให้ output JSON มี 3 field แต่ปัจจุบัน:

- `_NeedStatement` (`stages/need_combination.py:85-87`) ประกาศแค่ `statement_th` / `statement_en`
- `models.Need` **ไม่มี** `rationale_th` เลย (ต่างจาก `PLO` ที่มี `rationale_th`)

งานจริงที่ตามมา: field บน `_NeedStatement` → field บน `Need` → column บน ORM → **migration**
→ ที่แสดงผลบน UI (`SkillExtraction.tsx` NeedCard / `PloReport.tsx` การ์ด Need)

**⚠️ กับดักที่ต้องรู้**: `test_the_prompt_asks_for_the_fields_the_caller_actually_parses`
วนเช็กว่า *ทุก field ของ `_NeedStatement` ปรากฏใน system prompt* — เป็นการเช็กทางเดียว
ถ้าเพิ่ม `rationale_th` เข้า **prompt** โดยไม่เพิ่มเข้า `_NeedStatement` **test ยังเขียว**
และ Pydantic จะทิ้งค่าที่โมเดลอุตส่าห์เขียนมาเงียบ ๆ → จ่าย token ฟรีโดยไม่มีใครรู้
ถ้าจะทำข้อนี้ ต้องเริ่มจาก schema ไม่ใช่จาก prompt

เหตุผลที่ guidance เขียนไว้เอง: *"รองรับ Traceability และการอธิบายในวิทยานิพนธ์"* — ถ้า
เป้าหมายคือใช้อธิบายในวิทยานิพนธ์ นี่เป็นเหตุผลที่หนักพอจะทำ แต่เป็นงานคนละก้อนกับรอบนี้

### ไม่ฟรี-2 · กฎ 10 เขียนขึ้นโดยอิงข้อมูลที่ prompt ไม่เคยได้รับ

กฎบอกว่า "หากความสามารถใดปรากฏซ้ำจากผู้มีส่วนได้ส่วนเสีย**หลายกลุ่ม** ให้ถือว่าเป็น
ความสามารถเด่น" — แต่ `build_summarize_need_prompt(skill_names, ksec, bloom_level, *,
note_th, program_context)` **ไม่มีข้อมูล stakeholder หรือความถี่เลย** มันเห็นแค่ชื่อทักษะ

ข้อมูลนั้นมีอยู่จริงบน `_Group` (`stakeholder_coverage`, `stakeholder_types`, `demand_score`)
แต่ไม่เคยถูกส่งเข้า prompt นี้ → กฎ 10 **ทำตามไม่ได้เลยตามที่เขียน** ต้องเปลี่ยน signature
ของ builder + จุดเรียกใน `need_combination` ก่อน

ทางที่ถูกกว่าถ้าอยากได้ผลนี้: ใช้ `demand_score`/`stakeholder_coverage` ที่คำนวณแล้วเลือก
ว่าจะ **ส่งชื่อทักษะตัวไหนเข้า prompt ก่อน** (ตอนนี้ตัดดิบที่ `skill_names[:30]`, `:124`)
แทนที่จะบอกโมเดลให้เดาเอง

### กฎ 3 — "ห้ามเพียงนำชื่อทักษะมาต่อกัน"

ของเดิมบังคับด้วยการนับจุลภาค: `looks_like_a_skill_list` = `count(",") + count("，") > 2`
(`need_grouping.py:174-176`) และ prompt พูดถึงจุลภาคตรง ๆ (`:112-113`)

❌ example ของ guidance คือ **`ต้องการการใช้ AI การแปล และการตรวจแก้คำแปล`** —
**จุลภาค 0 ตัว** ผ่าน `looks_like_a_skill_list` สบาย ๆ ทั้งที่เป็นการต่อชื่อทักษะชัด ๆ
ภาษาไทยแจกแจงด้วยเว้นวรรคกับ `และ` ไม่ใช่จุลภาค heuristic เดิมจึงจับได้เฉพาะรูปที่โมเดล
เขียนแบบฝรั่ง

**นี่คือช่องโหว่จริง และควรแก้ที่ code ไม่ใช่แค่ขอ prompt ดี ๆ** — precedent มีอยู่แล้ว:
`find_vague_phrase` / `find_code_identifier` คืน *ตัววลีที่ผิด* ให้ retry prompt อ้างถึงได้
(`need_grouping.py:158-171`) ซึ่งได้ผลกว่าบอกว่า "ประโยคไม่ถูกต้อง"

### กฎ 9 — คำกว้างสองตัวที่หลุด regex

`_VAGUE_HEAD_RE` (`need_grouping.py:135-138`) จับ
`(ความรู้|ทักษะ|สมรรถนะ|ความสามารถ|คุณลักษณะ|สิ่ง|เรื่อง|ด้าน|งาน)` **ตามด้วย**

## §สิ่งที่ต้องทำก่อนไฟล์นี้จะเป็น prompt ได้

ถ้าวันหนึ่งตัดสินใจเอาเนื้อ guidance ไปใช้จริง (ไม่ว่าจะ copy เข้า Python literal หรือ
โหลดไฟล์) ต้องจัดการก่อน:

1. **ตัดตารางท้ายไฟล์** บรรทัด ~396–478 (`ประเด็น / Prompt เดิม / Prompt ปรับปรุง / เหตุผล`)
   — เป็นบันทึกเหตุผล ไม่ใช่คำสั่งถึงโมเดล และ flatten จนเสีย pipe ไปแล้ว
   (`skill_extraction.md` เป็นไฟล์เดียวใน 4 ไฟล์ที่จบสะอาดที่ output schema)
2. **`{MIN_STATEMENT_CHARS}`** (บรรทัด 391) เป็น placeholder ค้าง ต้อง substitute จาก
   `summarize_need.MIN_STATEMENT_CHARS` (= 40) ไม่งั้นโมเดลจะเห็นปีกกาดิบ
3. **เติมช่อง `program_context`** — guidance ไม่มีเลย ของเดิมมี `context_rule` ที่โผล่
   **เฉพาะเมื่อมี context** (`:88-92`) พร้อม `บริบทหลักสูตร:` ใน user message (`:125`)
   ทิ้งไปคือทิ้งสิ่งที่กัน "การดูแล" ไม่ให้ตีความผิดสาขา
4. **เติมช่อง designer note** — ของเดิมปิดท้าย system ด้วย `NOTE_POLICY_TH` (`:120`)
   และ `append_note(user, note_th)` (`:134`) guidance ไม่มีที่ทางให้
5. **ระวังถ้อยคำที่ test จับแบบ exact substring** — guidance เขียน
   `ห้ามเพิ่มเนื้อหาที่ไม่มี**อยู่**ในกลุ่มทักษะ` แต่ test ยืนยันสตริง
   `ห้ามเพิ่มเนื้อหาที่ไม่มีในกลุ่มทักษะ` (ไม่มี "อยู่") → คำเดียวต่างกัน test แดง

**test ที่จะแดงถ้าเอา guidance ไปทับตรง ๆ** (จาก 17 ตัวที่เขียวอยู่ตอนนี้):

- `test_summarize_prompt_offers_every_allowed_opening` (×4 params) — opening หาย
- `test_summarize_prompt_forbids_inventing_content_from_the_context` — ถ้อยคำต่าง
- `test_summarize_prompt_no_longer_mandates_the_labour_market_frame` — ขึ้นกับถ้อยคำที่เลือก
- `test_summarize_prompt_carries_the_program_context` — ถ้าไม่เติมช่อง context
