# 01 — ประธานของประโยค Need: คง `บัณฑิต/หลักสูตร` หรือย้ายไป `ผู้ปฏิบัติงาน`

> ใบนี้ควรตัดสิน **ก่อน** ticket 14: ตัวเลือก (ค) ของใบนั้นคือการแปลงข้อเรียกร้องฝั่งสถาบัน
> ให้เป็น "ฝั่งบัณฑิต" ซึ่งเป็นคำที่ใบนี้กำลังตัดสินว่าจะยังมีอยู่ไหม

## Question

`guidances/market_need_synthesis.md` เขียนประธานของทุก ✅ example เป็น
**`ต้องการผู้ปฏิบัติงานที่สามารถ...`** ขณะที่ prompt ที่รันอยู่เสนอ 4 แบบ
(`ต้องการ...` / `ต้องการบัณฑิตที่...` / `ต้องการหลักสูตรที่...` / `บัณฑิตต้องมี...`)
และ role line เขียนว่า "ความต้องการที่มีต่อ**บัณฑิตและหลักสูตร**"

รับหรือไม่รับ ต้องตอบเป็นการตัดสินใจ ไม่ใช่การปรับถ้อยคำ

## ทำไมไม่ใช่การปรับถ้อยคำ

opening อิสระเป็นผลของ 3 commit ที่มีเหตุผลบันทึกไว้:

- `a5823b9` ถอด opening บังคับ `ตลาดแรงงานต้องการ` — มันไม่ได้บอกอะไรที่ประโยคที่เหลือ
  ไม่ได้บอก และกินตัวอักษรไปจาก floor 40
- `e09b2d6` ตามไปแก้ prompt ปลายน้ำ 3 ตัวที่เขียนโดยสมมติว่า Need เปิดด้วยวลีนั้น —
  commit message บอกเองว่าเส้นแบ่ง "เสียงตลาด vs เสียงผู้เรียน" ใช้ไม่ได้แล้ว
  เส้นแบ่งจริงคือ **ข้อกำหนด vs ผลลัพธ์**
- `45692f2` "stop asking every stakeholder what the labour market wants" — แก้ปัญหา
  framing เดียวกันนี้ที่ชั้นสกัด

`ผู้ปฏิบัติงาน` พา framing กลับไปทางที่ 3 commit นั้นเดินออกมา และ Need ไม่ได้มาจาก
นายจ้างอย่างเดียว — `institutional_direction`, `student`, `alumni` ก็ผลิต Need

## สิ่งที่ต้องกดให้แตกก่อนตอบ

1. **guidance ขัดกฎตัวเอง** — กฎข้อ 2 ห้าม `สามารถ...ได้` แต่ ✅ example ทุกตัวเขียน
   `ต้องการผู้ปฏิบัติงานที่**สามารถ**...` อ่านตามตัวอักษรแล้วตัวอย่างตกกฎของตัวเอง
   → เจตนาจริงน่าจะห้าม *รูปผลลัพธ์การเรียนรู้* (ประธานเป็น บัณฑิต/ผู้เรียน + ปิดด้วย `ได้`)
   ไม่ใช่ห้ามคำว่า `สามารถ` ต้องแยกให้ออกก่อน ไม่งั้นจะรับกฎที่ตีความไม่ตรงกัน
2. **ถ้ารับ ต้องแก้อะไรบ้าง** — `test_summarize_prompt_offers_every_allowed_opening`
   (parametrize 4 แบบ), `test_summarize_prompt_keeps_the_subject_this_repo_already_chose`
   (ยืนยันว่า `ผู้ปฏิบัติงาน` **ไม่** อยู่ใน prompt — ใบนี้คือสิ่งที่ปลดล็อกมัน),
   docstring ของ `build_summarize_need_prompt`, บล็อกใน CLAUDE.md
3. **ถ้าไม่รับ กฎข้อ 2 เหลืออะไร** — เจตนา "ห้ามรูปผลลัพธ์การเรียนรู้" มีอยู่แล้วที่
   `summarize_need.py` (`ห้ามเขียนเป็นผลลัพธ์การเรียนรู้ (PLO) ที่เสร็จรูปแล้ว`)
   → กฎ 2 กลายเป็น "ซ้ำของเดิม" ไม่ต้องแก้อะไรเลย
4. **Need ที่มาจากสถาบัน จะเขียนด้วยประธานไหน** — `ต้องการผู้ปฏิบัติงานที่...` อ่านแปลก
   กับ Need ที่มาจากวิสัยทัศน์ของคณะเอง ถ้ารับ ต้องตอบว่าเคสนี้เขียนยังไง

## ผลลัพธ์ที่ต้องได้

รับ / ไม่รับ / รับบางส่วน พร้อมเหตุผลที่เขียนทับ docstring เดิมได้
ถ้า "ไม่รับ" ให้ปิดใบนี้และบันทึกว่ากฎ 2 ของ guidance = ซ้ำของเดิม

## คำตัดสิน — 2026-09-18: **คง `บัณฑิต/หลักสูตร` ไม่รับ `ผู้ปฏิบัติงาน`**

opening ทั้ง 4 แบบอยู่เหมือนเดิม role line ของ `summarize_need` อยู่เหมือนเดิม
ไม่มีการแก้โค้ดจากใบนี้ — สิ่งที่เปลี่ยนคือมันกลายเป็นคำตัดสินที่มีเหตุผลบันทึกไว้
แทนที่จะเป็นสภาพเดิมที่ยังไม่มีใครตั้งคำถาม

**สิ่งที่ตามมาโดยอัตโนมัติ:**

1. **กฎข้อ 2 ของ guidance = ซ้ำของเดิม** เจตนาจริงของมัน (ห้ามรูปผลลัพธ์การเรียนรู้)
   `summarize_need.py` ทำอยู่แล้วที่บรรทัด `ห้ามเขียนเป็นผลลัพธ์การเรียนรู้ (PLO) ที่เสร็จรูปแล้ว`
   ส่วนที่ห้ามคำว่า `สามารถ` แบบเหมารวมไม่รับ เพราะ ✅ example ของ guidance เองก็ใช้คำนั้น
2. **ชน-A ใน [three-file-review](../three-file-review.md) ปิดตามไปด้วย** — role line ของ
   `extract_skills` ที่เขียนว่า "ทักษะที่ตลาดแรงงานต้องการ" **ไม่รับ** ด้วยเหตุผลเดียวกัน
   และแรงกว่าด้วย เพราะที่ชั้นสกัดมันทำให้ธง `is_graduate_capability` ไร้ความหมาย
   (framing ที่กรองกิจกรรมสถาบันทิ้งตั้งแต่ต้น ทำให้ไม่มีอะไรเหลือให้ติดธง)
3. **ticket 14 ไม่ถูกบล็อกแล้ว** — ตัวเลือก (ค) ของใบนั้น ("แปลงข้อเรียกร้องฝั่งสถาบัน
   เป็นฝั่งบัณฑิต") อ่านได้ตรงตัวแล้ว เพราะ "ฝั่งบัณฑิต" ยังเป็นคำที่ prompt ใช้จริง

**test ที่ตรึงคำตัดสินนี้**: `test_summarize_prompt_keeps_the_subject_this_repo_already_chose`
(ยืนยันว่า `ผู้ปฏิบัติงาน` ไม่อยู่ใน prompt และ opening ครบทั้ง 4) ·
`test_the_task_line_does_not_narrow_the_corpus_to_the_labour_market` ·
