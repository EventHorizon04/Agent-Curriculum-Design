# 14 — ผลรัน pipeline เต็มครั้งแรก และการเปลี่ยนกฎ any เป็นสัดส่วน

หลักฐานที่ทำให้ [ticket 04](../issues/04-two-axis-flags-on-need.md) และ
[ticket 11](../issues/11-two-axis-selection.md) ถูกแก้หลังปิดไปแล้ว — ทั้งสองใบตัดสิน
กฎ any จากตัวเลข recall รายทักษะ ซึ่งเป็นตัวเลขเดียวที่มีตอนนั้น

**ชุดข้อมูล**: `program-3` — evidence 14 ชิ้นชุดเดียวกับ prototype ทั้งหมด อัปโหลดผ่าน API
จริง มี `scope_th` (รูป `C_narrow`) ครบ, `EXTRACTION_PROVIDER=ollama`
`HEAVY_PROVIDER=ollama` (`gemma4:31b-cloud`), light/synthesis เป็น opentyphoon ตาม default

## ข้อผิดพลาดของการรันรอบแรก — บันทึกไว้เพราะจะเกิดซ้ำ

รอบแรก POST evidence แล้วข้ามไปสกัดทักษะเลย **โดยไม่เรียก
`GET /evidence/classify-stream`** ซึ่งคือตัว stage stakeholder needs

`POST /evidence/` ไม่ classify ให้ — evidence ทั้ง 14 ชิ้นจึงเป็น `general` →
ทักษะทั้งหมดเป็น `want` → `is_optional_group()` ตัดสินว่าทุกกลุ่มเป็น optional →
**PLO ออกมาเป็น `OPT1..OPT10` ทั้งหมด core = 0**

ไม่ใช่บั๊ก แต่เป็นลำดับที่ UI ทำให้อยู่แล้วและคนที่เรียก API ตรงต้องรู้

## การรันที่ถูกต้อง — กฎ any

| | ค่า |
|---|---|
| evidence | 14 (`requirement` 5) |
| skills | 59 |
| skills ติดธงนอกสาขา | 14 |
| skills ติดธงไม่ใช่สมรรถนะบัณฑิต | 11 |
| Needs | 10 |
| **Need ถูกกรอง** | **1** |
| core / optional PLO | 3 / 6 |
| contamination (span หาไม่พบในหลักฐาน) | **0** |

`contamination = 0` ยืนยัน [ticket 13](../issues/13-scope-position.md) บน pipeline จริง:
scope statement อยู่ใน system prompt แล้วไม่รั่วมาเป็นหลักฐาน

**แต่ Need ที่ควรถูกกรองสองใบรอด** และหนึ่งในนั้นขึ้นเป็น core PLO อันดับสอง:

| Need | in-field | graduate | ผลใต้กฎ any |
|---|---|---|---|
| ออกแบบและสร้างเครือข่ายความร่วมมือระดับนานาชาติ | **1/7** | **2/7** | ผ่าน → core PLO (demand 0.30) |
| ออกแบบหลักสูตรการเรียนการสอนภาษาจีน-ไทย | 4/6 | **2/6** | ผ่าน → optional PLO |
| ออกแบบและพัฒนาโครงการบริการวิชาการ | 0/3 | 1/3 | กรอง |

ใบแรกคือ **ตัวอย่างที่ map ยกมาตั้งแต่บรรทัดแรก**ว่าเป็น "อยู่ในสาขาแต่ไม่ใช่สิ่งที่บัณฑิตทำ"
สมาชิกติดธงนอกสาขา 6 ใน 7 และติดธงไม่ใช่สมรรถนะบัณฑิต 5 ใน 7 — แต่กฎ any ต้องการ
แค่สมาชิกเดียวรอด

**รากของปัญหาไม่ใช่ recall ของธง แต่คือ `need_combination` รวมทักษะข้าม evidence**
เมื่อ Need หนึ่งมีสมาชิกหกเจ็ดตัว เงื่อนไข "มีสมาชิกหลุดธงอย่างน้อยหนึ่ง" แทบเป็นจริงเสมอ
ตอนตัดสิน ticket 04 ไม่มีใครวัดตัวนี้

## กวาดค่า threshold บน Need สิบใบเดียวกัน

ตัดสินด้วยมือก่อนกวาดว่าสามใบไหนควรถูกกรอง (ทั้งสามพูดถึงสิ่งที่สถาบันทำ)

| threshold | กรองได้ | ควรกรองแต่รอด | กรองผิด | core PLO |
|---|---|---|---|---|
| `> 0` (กฎ any) | 1 | **2** | 0 | 3 |
| 0.25 | 2 | 1 | 0 | 2 |
| 0.34 | 3 | **0** | **0** | 2 |
| **0.50** | **3** | **0** | **0** | **2** |
| 0.60 | 3 | **0** | **0** | 2 |
| 0.75 | 4 | 0 | **1** | 1 |
| 1.00 | 5 | 0 | **2** | 0 |

**0.34-0.60 แยกได้สมบูรณ์เหมือนกันหมด** เลือก 0.5 เพราะอยู่กลางช่วง จึงเหลือระยะก่อน
คำตอบเปลี่ยนมากที่สุด — ไม่ใช่เพราะเป็นเลขกลม

ใบที่ทดสอบเกณฑ์ได้ดีที่สุดคือ **"ทักษะผู้ประกอบการ"** (67% / 100%) ซึ่ง
`Needs_to_PLO_TCISM.xlsx` เก็บไว้เป็น PLO4 — ทุกค่าตั้งแต่ 0.34 ถึง 0.60 ปล่อยผ่าน
ส่วน 0.75 กรองทิ้ง

## การรันซ้ำด้วยเกณฑ์สัดส่วน

รันบน `program-3` เดิม cache ของ extraction และ clustering hit ทั้งหมด
(**skill extraction 0 วินาที**) จึงได้ Need ชุดเดียวกัน — ตัวแปรเดียวที่เปลี่ยนคือกฎ

| | กฎ any | สัดส่วน 0.5 |
|---|---|---|
| Need ถูกกรอง | 1 / 10 | **3 / 10** |
| core PLO | 3 | **2** |
| optional PLO | 6 | 5 |
| รวม PLO | 9 | **7** |

PLO ที่เหลือทั้งเจ็ดเป็นงานแปล/ล่ามทั้งหมด ไม่มีใบไหนพูดถึงสิ่งที่สถาบันทำ

## สองอย่างที่การรันนี้ยืนยันนอกเหนือจากเกณฑ์

**1. ตัวเลขสองแกนในล็อกต่างกันแล้วจริง**

```
Stage 4: กรอง Need นอกขอบเขตออก 3 ใบ (นอกสาขา 2, ไม่ใช่สมรรถนะบัณฑิต 3)
```

[ticket 11](../issues/11-two-axis-selection.md) ยืนยันให้แยกตัวเลขสองแกนไว้ด้วยเหตุผลว่า
*"วันที่สองตัวไม่เท่ากันคือวันที่สองแกนเริ่มแยกกันจริง และเห็นได้จากล็อกทันทีโดยไม่ต้อง
รัน eval"* — ใบที่ต่างคือ "ออกแบบหลักสูตร" (67% ผ่านเกณฑ์สาขา แต่ 33% ตกแกนบัณฑิต)
ถ้ายุบเป็นตัวเลขเดียว สัญญาณนี้จะหายไป

**2. warning `MIN_NEEDS` แยกสาเหตุได้จริง**

```
Stage 4 produced 2 core PLOs, below the 6 minimum policy —
  กรอง Need นอกขอบเขตออก 3 ใบก่อนร่าง (หลักฐานในขอบเขตไม่พอ); review at the checkpoint
```

เทียบกับการรันรอบที่ไม่มี Need ถูกกรอง ซึ่งบรรทัดเดียวกันเขียนว่า
*"need_combination should have enforced this"* — สองสาเหตุอ่านต่างกันได้ตามที่
[ticket 05](../issues/05-synthesis-selection-filter.md) ออกแบบ

## ข้อจำกัด

- Need สิบใบจากหลักสูตรเดียว ปรับค่าให้เข้ากับตัวเองได้ง่าย
  `scripts/eval_scope_guard.py` คือตัวที่ทบทวนค่านี้เมื่อมีคลังกว้างขึ้น
- "ควรถูกกรอง" ตัดสินด้วยมือจากประโยค Need ไม่ใช่จากเฉลยมนุษย์โดยตรง —
  `Needs_to_PLO_TCISM.xlsx` เป็นเฉลยของ Need คนละชุดที่มนุษย์เขียนเอง
- core PLO = 2 ต่ำกว่าพื้น 6 มาก ซึ่งเป็นผลที่ถูกต้องของคลังนี้ (evidence 14 ชิ้น
  มี `requirement` แค่ 5) ไม่ใช่ข้อบกพร่องของเกณฑ์
