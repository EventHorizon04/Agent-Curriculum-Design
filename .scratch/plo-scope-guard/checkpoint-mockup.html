Need ที่ถูกกัน โชว์ยังไงให้ตัดสินได้ในไม่กี่วินาที

วันนี้หน้า PLO report มีก้อนเดียวชื่อ “Need ที่ไม่ได้เป็น PLO” ซึ่งรวมทุกสาเหตุไว้ด้วยกัน ตอนนี้สาเหตุมีสามแบบ และ designer ต้องทำคนละอย่างกับแต่ละแบบ — สามทางเลือกข้างล่างใช้ palette และโครงเดียวกับหน้าจริง ต่างกันแค่วิธีจัดก้อน

สามก้อนแยกกัน

ทางเลือก C

สองก้อน — “ยอมรับได้” กับ “ต้องอ่าน”

แบ่งตามสิ่งที่ designer ต้องทำ ไม่ใช่ตามกลไกที่กันมันออก: แพ้เพดานคือไม่ต้องทำอะไร ส่วนสองแกนรวมกันคือของที่ต้องอ่านว่าโมเดลตัดสินถูกไหม โดยมีป้ายบอกว่าแกนไหน

สิ่งที่ต้องตัดสินจาก mockup นี้

1 · จัดก้อนแบบไหน
A แยกตามกลไกที่กันมันออก · B ไม่แยกเลย ใช้ป้าย · C แยกตามสิ่งที่ต้องลงมือทำ. ข้อมูลที่มี: ธงสองแกนทับกันเกือบทุกใบบนคลังที่ evidence อยู่ในสาขาทั้งหมด แปลว่าก้อน “นอกสาขา” กับ “ไม่ใช่สมรรถนะบัณฑิต” ของทางเลือก A จะมีสมาชิกซ้ำกันเป็นประจำ ซึ่งเป็นเหตุผลที่ทำให้ A อ่านสับสนกว่าที่คิดตอนออกแบบ
2 · แต่ละรายการแสดงอะไรบ้าง
ตอนนี้ mockup แสดง: statement · demand score · สัดส่วนสมาชิกที่ผ่าน (0 / 5) · ชื่อทักษะสมาชิก · evidence span หนึ่งบรรทัด · ป้ายสภาวิชาชีพ. อันไหนเกิน อันไหนขาด — span ยาวสุดในชุดจริงคือหลายบรรทัด ตัดทิ้งหรือให้กดขยาย
3 · อยู่ที่หน้าไหน
หน้า PLO Report มีก้อน “Need ที่ไม่ได้เป็น PLO” อยู่แล้ว — ต่อยอดที่นั่นได้เลย. แต่หน้า PLO Synthesis คือที่ที่ designer กด “รวมเป็น PLO เดียว” ซึ่งเป็นทาง override ทางเดียว. โชว์ที่เดียว สองที่ หรือโชว์เต็มที่ report แล้วมีบรรทัดสรุปที่ synthesis
4 · ถ้อยคำ “ต้องรันอะไรใหม่บ้าง”
กลไกจริง: scope statement อยู่ใน cache key ของการสกัดทักษะ → แก้ scope = สกัดใหม่ทั้งโปรแกรม → need combination รันตามเพราะใช้ checkpoint เดียวกัน. mockup เขียนว่า “แก้ที่หน้า Intake แล้วรันสกัดทักษะใหม่ทั้งโปรแกรม — Need จะถูกสร้างใหม่ตามไปเอง” — ชัดพอไหม และควรมีปุ่มลัดไปหน้า Intake ไหม (ระบบไม่ re-run ให้เอง โดยเจตนา — ชน rule 7)
5 · ป้ายสภาวิชาชีพควรมีไหม
การรัน eval จริงพบว่า guard กรอง Need ที่มีสมาชิกเป็นข้อกำหนดจากสภาวิชาชีพ 1-2 ใบต่อรอบ — classification ไม่เคยไปถึงตัวกรอง. ป้ายนี้ทำให้ designer เห็นก่อนอนุมัติ แต่ก็เป็นการแก้ปัญหาที่ UI ทั้งที่รากอยู่ที่นโยบาย (จุดที่ยังไม่ตัดสินข้อ 8)
