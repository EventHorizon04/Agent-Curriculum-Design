01 ปัญหาและสองแกน

demand_score วัดว่า “ตลาดพูดถึงเรื่องนี้บ่อยแค่ไหน” อย่างเดียว ไม่ได้วัดว่าเรื่องนั้นเป็นของหลักสูตรนี้หรือเปล่า. ทักษะที่วิสัยทัศน์สถาบันหรือผู้บริหารพูดถึงซ้ำ ๆ จึงไต่ขึ้นอันดับต้น ๆ แล้วกลายเป็น PLO ทั้งที่ไม่ใช่สิ่งที่บัณฑิตทำ หรือไม่ใช่สาขาของหลักสูตรเลย

ExtractedSkill.is_field_relevant มีอยู่แล้วในโค้ด แต่ตายที่ need_combination — ไม่มีอะไรกรองด้วยมัน cluster_skills.py:36 สั่งเก็บทักษะนอกสาขาไว้ในกลุ่มโดยเจตนา และ demand_score ก็ไม่มีเทอมของสาขาเลย

  • เกณฑ์ scope ใน SMART gate — ถึงจุดนั้นจ่ายค่า synthesis ไปแล้ว

04 scope statement

ช่อง free text ช่องเดียวที่ intake เก็บลง ProgramCreateRequest.scope_th (สืบทอดถึง ProgramMetadata) ค่าเริ่มต้นเป็นสตริงว่าง

รูปที่พิสูจน์แล้วว่าใช้ได้

เขียนแคบ แจกแจงเป็นรายการ ฝั่งบวกล้วน — บอกว่าหลักสูตรครอบคลุมอะไร ไม่ใช่ไม่ครอบคลุมอะไร

รายการ “ไม่รวมถึง” ได้ศูนย์ และเป็น variant เดียวที่สร้าง false positive — มันจับเฉพาะของที่อยู่ในรายการเป๊ะ ๆ แล้วปิดวิจารณญาณกับอย่างอื่น

เขียนกว้างหรือลอย ๆ ได้ 25% ต่ำกว่า control ที่ 33% — scope ที่ไม่คมไม่ใช่แค่ไม่ช่วย แต่ทำให้โมเดลมั่นใจผิด

ฟอร์มที่ intake

  1. เขียนเฉพาะสิ่งที่หลักสูตรครอบคลุม แจกแจงเป็นรายการ 3-4 อย่าง
  2. อย่าเขียนรายการ “ไม่รวมถึง” — จากการทดสอบ รายการกันออกทำให้ระบบตัดสินแย่ลงกว่าไม่เขียนอะไรเลย
  3. เขียนกว้าง ๆ หรือลอย ๆ แย่กว่าไม่เขียน — ถ้ายังแจกแจงไม่ได้ ให้เว้นว่างไว้ก่อน

B_broad ยาว ~90 ตัวอักษรแบบบรรยายรวม ๆ ไม่พอ ส่วน C_narrow ~150 ตัวอักษรแจกแจง 4 รายการพอ — ความยาวเป็นผลพลอยได้ของการแจกแจง ไม่ใช่ตัวชี้วัด ไม่ใส่ validator ความยาว

05 prompt กับสคีมา

scope statement อยู่ใน system prompt

ต่อท้ายบล็อกกติกา ก่อนบรรทัด "ตอบเป็น JSON object:" แบบมีเงื่อนไข — ไม่มี scope ก็ไม่มีบรรทัดนี้ prompt เดิมเป๊ะ

# ถ้อยคำที่ทดสอบแล้ว ต้องมีทั้งสองประโยค
- ขอบเขตของหลักสูตรนี้: {scope_th}
  ใช้บรรทัดนี้เป็นเกณฑ์ตัดสิน is_field_relevant เท่านั้น ห้ามสกัดทักษะจากบรรทัดนี้
  ทักษะทุกรายการต้องมาจากข้อความ evidence เท่านั้น
ห้ามวางไว้ใน user message

วางติดข้อความหลักฐานแล้วโมเดลอ่าน scope statement เป็นหลักฐาน — วัดได้ 8 ทักษะที่ทั้งชื่อและ evidence_span_th ลอกจาก scope คำต่อคำ บน evidence สองชิ้นที่สั้นที่สุด (148 และ 348 ตัวอักษร) ซึ่งไม่มีคำเหล่านั้นอยู่ในข้อความเลย

รูปนี้อันตรายกว่าที่เห็น: span คัดลอกตรงตัวจริง แต่คัดจาก scope ไม่ใช่จากหลักฐาน วันที่ scope บังเอิญมีวลีตรงกับหลักฐาน is_grounded() จะปล่อยผ่าน แล้วรอยเท้ากลับไปหาหลักฐานจะชี้ผิดที่โดยไม่มีใครรู้ — ชน immutable rule 2 ตรง ๆ

ย้ายไป system prompt แล้วเหลือ 0 โดยที่ recall (4/8) และ false positive (1) เท่าเดิมทั้งสองตำแหน่ง — ไม่ได้แลกอะไรเลย

ธงแกนที่สองในสคีมา

เพิ่ม is_graduate_capability: bool = True ใน _SkillItem และบรรยายไว้ในสคีมาที่ prompt เขียน พร้อมกติกาหนึ่งข้อ

- is_graduate_capability = true เมื่อทักษะนั้นเป็นสิ่งที่บัณฑิตคนหนึ่งทำได้เมื่อ
  สำเร็จการศึกษา; false เมื่อเป็นกิจกรรมหรือภารกิจของสถาบัน/หลักสูตร (เช่น การ
  บริหารหลักสูตร การจัดหางบประมาณ การสร้างความร่วมมือระดับองค์กร)
  ให้คงไว้แต่ตั้งเป็น false ห้ามตัดทิ้งเอง
ห้ามให้โมเดลตัดทิ้งเอง และห้ามให้เขียนชื่อใหม่

กติกาที่สั่งให้ตัดทิ้ง ลดทักษะจาก noise ได้จริง (9→5) แต่ลาก CORE ลงไปด้วย (29→26) และลากทักษะจากวิสัยทัศน์สถาบันลงไปมากที่สุด (20→14) โดยไม่มีร่องรอยว่าตัดอะไร — ตรวจสอบไม่ได้เลย

กติกาที่ให้เขียนชื่อทักษะใหม่ ผลิตการเขียนใหม่ 45 ครั้ง และหลายครั้งแต่งเติมความเฉพาะที่หลักฐานไม่ได้พูด — “การนำเทคโนโลยี AI มาปฏิรูปการศึกษา” กลายเป็น “การใช้ปัญญาประดิษฐ์ในงานแปลและล่าม” ชื่อทักษะไม่ตรงกับ span ที่ต้องคัดลอกตรงตัวอีกต่อไป

มนุษย์เขียนใหม่จริง แต่เขียนที่ระดับ Need ตอนที่หลักฐานถูกเก็บครบแล้ว ที่ทางของมันคือ summarize_need ไม่ใช่ extract_skills

06 cache กับ contract

cache_key

ต่อ scope_th เข้าไปแบบไม่มีเงื่อนไข — …\x00{field_th}\x00{program_name_th}\x00{scope_th} แม้ว่าง

เดิมตั้งใจทำแบบมีเงื่อนไขเพื่อรักษาแถวเก่าให้ยังหยิบได้ แต่ธงใหม่ในสคีมาทำให้ contract ขยับอยู่ดี ไม่มี key เดิมให้รักษาแล้ว conditional จึงเหลือแต่ต้นทุน: branch ที่ต้องมี test คุ้มตลอดไป แลกกับประโยชน์ครั้งเดียวที่ไม่ได้เกิด

fingerprint()

scope_th ต้องไม่เข้า fingerprint — เพิ่ม parameter เป็น scope_th: str = "" แบบมีเงื่อนไข แล้ว fingerprint ยังคำนวณจาก prompt ที่ไม่มีบรรทัด scope

fingerprint คือสัญญาเรื่องรูปร่างของ payload ซึ่งไม่แปรตามโปรแกรม ส่วน scope เป็น per-program input เหมือน field_th ที่อยู่ใน cache key แยก ถ้ามีคนทำให้ scope เข้า fingerprint ทุกโปรแกรมจะมี contract คนละค่า แล้ว prune_cache จะรายงาน stale-contract มั่วทั้งตาราง — เขียนคอมเมนต์กำกับไว้ในโค้ด

การ deploy

re-extract หนึ่งรอบ ทำครั้งเดียวจบ — ธงใหม่ scope statement และกติกาใหม่ไปพร้อมกันใน migration เดียว ไม่ทยอยแก้แล้วจ่ายสองรอบ

ไม่สั่ง prune_cache --delete ก่อน deploy — นั่นคือเอา irreversible action มาไว้ก่อนจุดที่ยังถอยได้ ถ้าต้อง rollback แถวเก่ายังใช้ได้ถ้ายังไม่ลบ กวาดหลังจากมั่นใจแล้ว

ไม่เตือนใน UI — คำเตือนต้องรู้ว่า cache ของโปรแกรมนี้ stale ซึ่งแปลว่าต้อง query llm_cache เทียบ contract ก่อนเรนเดอร์หน้า โครงสร้างใหม่ทั้งชุดเพื่อข้อความที่แสดงครั้งเดียวในชีวิตของ deployment

หลังรอบใหญ่
โปรแกรมที่แก้ scope statement ทีหลัง re-extract เฉพาะตัวเอง — ผลตรงจากการที่ scope อยู่ใน key ไม่ใช่ใน contract

09 is_in_scope()

อยู่ใน stages/need_grouping.py ข้าง MIN_NEEDS และ MAX_CORE_PLOS — เป็น policy ตัวที่สามที่ตัดสินว่า Need ไหนได้เป็น PLO เหมือนกันกับสองค่าเดิม

def is_in_scope(need: Need) -> bool:
    """ผ่านต้องผ่านทั้งสองแกน; ถูกกันเมื่อ OFF แกนใดแกนหนึ่ง."""
    return need.is_field_relevant and need.is_graduate_capability

คืน bool เท่านั้น — เหตุผลว่าตกเพราะแกนไหนมาจาก counter สองตัวบน Need ฟรี ๆ ตัวไหนเป็น 0 คือแกนนั้น และได้ละเอียดกว่า enum ด้วย (“0 ใน 8” ไม่ใช่แค่ off_field)

ทำไม any ที่ระดับ skill แต่ and ที่ระดับแกน

ทั้งสองอย่างเป็นการเลือกฝั่งปล่อยผ่าน: Need ผ่านแกนหนึ่งได้ด้วยสมาชิกเพียงคนเดียว (any) เพราะ recall อยู่ที่ 56% — สัญญาณที่พลาดครึ่งหนึ่ง ถ้าใช้ majority จะตัดของถูกทิ้ง. ส่วน and ระหว่างสองแกนไม่ได้ทำให้กรองแรงขึ้นในทางปฏิบัติ เพราะวัดแล้วว่าธงสองแกนทับกัน 100% ไม่มีทักษะตัวใดติดธงแกนเดียว

แก้หลังรัน eval จริง — spec ฉบับแรกเขียนข้อนี้ผิด

เดิมเขียนว่า “requirement wins เป็นกฎที่ตั้งใจให้ guard กรองไม่ได้” และให้รายงานว่า “กรองไม่ได้ N ใบ เพราะเป็น requirement — ถูกต้องตามนโยบาย” ไม่จริงทั้งคู่

requirement wins ตัดสิน classification เท่านั้น ส่วน is_in_scope() อ่าน counter บน Need ซึ่งนับจากธงดิบรายแถว — classification ไม่เคยไปถึงมันเลย. ทักษะที่สภาวิชาชีพสั่งแล้วโมเดลตีว่านอกสาขา ถูกกรองเหมือนของอื่นทุกประการ

ที่มาของความผิด: ยกกฎมาจาก ticket 04 ซึ่งพูดถึงมันในบริบทของ classification ล้วน ๆ แล้วอนุมานต่อเองว่าปกป้องการกรองด้วย โดยไม่มีใครไล่เส้นทางจาก classification ไปถึง is_in_scope — ซึ่งไม่มีเส้นทางนั้น. การรันจริงยืนยัน: 1-2 Need ต่อรอบถูกกรองทั้งที่มีสมาชิกเป็น requirement

ตัดสินแล้วว่าให้เป็นแบบนี้ต่อไป — requirement ไม่ได้รับการยกเว้น: “requirement wins” ตัดสินว่าทักษะเป็นข้อกำหนดไหม ซึ่งคนละคำถามกับว่าสมรรถนะนั้นเป็นของหลักสูตรนี้ไหม สภาวิชาชีพสั่งสิ่งที่หลักสูตรนี้ไม่ใช่ที่ทางที่จะสอนได้. แทนที่จะยกเว้นในโค้ด: ติดป้ายที่ report ให้ designer เห็นก่อนอนุมัติ และ merge route ไม่กัน จึงหยิบกลับได้

B0 = branch เดิมก่อนธงใหม่ · B1 = branch ใหม่ scope ว่าง

B1 − B0 = ช่องธงที่สองให้อะไร · ผล − B1 = scope statement ให้อะไร

สมมติฐานเดิมที่ว่า “ไม่มี scope = พฤติกรรมเดิมเป๊ะ จึงเป็น test ในตัว” ใช้ไม่ได้แล้ว: การเพิ่มช่องธงดันธงสาขาจาก 3/9 เป็น 5/9 ทั้งที่ไม่มี scope. ยังจริงที่ระดับ prompt bytes ของบรรทัด scope แต่ไม่จริงที่ระดับผลลัพธ์

metric ทุกรอบ
  1. recall / FP ที่ระดับ Need แยกสองแกนและรวม
  2. recall / FP ที่ระดับ skill (diagnostic)
  3. overlap ของสองแกน (ตาราง 2×2) — ตัวที่ตัดสินว่าเก็บสองคอลัมน์ไว้ถาวรคุ้มไหม
  4. contamination — ทักษะที่ชื่อหรือ span ลอกวลีจาก scope statement เป็น metric ถาวร ไม่ใช่วัดครั้งเดียวแล้วเลิก เพราะยังไม่รู้ว่า scope ที่ยาวกว่า ~150 ตัวอักษรจะเริ่มปนไหม
  5. จำนวน Need ที่ ถูกกรองทั้งที่มีสมาชิกเป็น requirement — สัญญาณเตือน ไม่ใช่การยืนยันว่ากฎทำงานถูก: สมรรถนะที่มีอำนาจตามกฎหมายสั่งไว้ ถูกตัดทิ้งตามคำโมเดลที่ recall แค่ครึ่งเดียว
ถ้าไม่ผ่าน
ปิดสวิตช์กรอง เหลือแต่ติดธงให้ designer ดูที่ checkpoint — หน้านั้นมีอยู่แล้ว การถอยจึงไม่ต้องเขียนอะไรใหม่ และเป็นเหตุผลเพิ่มที่ is_in_scope() ต้องเป็น predicate เดียวเรียกที่เดียว
รันเมื่อไหร่

manual — สคริปต์ใน scripts/ รันเมื่อแตะ prompt เปลี่ยน model หรือย้าย slot. ไม่ใช่ CI: เรียก LLM จริง 28–70 call ต่อรอบ และไม่ deterministic พอจะเป็น gate สีแดง/เขียว

สิ่งที่อยู่ใน CI คือ unit test ของ is_in_scope() และ cache key ซึ่ง deterministic ล้วน — eval เป็นเครื่องมือตัดสินใจของคน ไม่ใช่ด่านอัตโนมัติ

  7. merge route ไม่กรอง — Need นอกขอบเขตยัง merge ได้ ตอบ 200 และมี log
