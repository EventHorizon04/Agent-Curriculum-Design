# 06 — checkpoint กับ report โชว์ Need ที่ถูกกันยังไง

Map: [PLO synthesis ที่ไม่หลุด scope ของหลักสูตร](../map.md)
Type: prototype
Status: resolved
Blocked by: 05 (resolved), 11 (resolved)

## Question

ตกลงแล้วว่าแยกสองก้อน: **"แพ้ demand"** กับ **"นอกขอบเขตหลักสูตร"** เพราะ designer
ต้องทำคนละอย่าง — แพ้ demand คือยอมรับได้ ไม่ต้องทำอะไร; นอกขอบเขตคือต้องอ่านว่า model
ตัดสินสาขาถูกไหม ถ้าผิดแปลว่า scope statement เขียนไม่ดี

ทำ prototype ของหน้าที่ designer เห็นจริง เพื่อตอบ:

- แต่ละรายการในก้อน "นอกขอบเขต" ต้องแสดงอะไรถึงจะตัดสินได้ในไม่กี่วินาที — statement ของ Need,
  ชื่อ skill สมาชิก, สัดส่วน in-field, evidence span, demand_score ที่จะได้ถ้าไม่ถูกกัน?
- ถ้า designer อ่านแล้วเห็นว่าผิด ทางไปต่อคืออะไร — ข้อความบอกว่า "แก้ scope statement
  แล้ว re-run skill extraction" จะเขียนยังไงให้ไม่กำกวมว่าต้องรันอะไรใหม่บ้าง
  (ตกลงไว้ว่าระบบเตือนอย่างเดียว ไม่ re-run ให้เอง เพราะจะชน immutable rule 7)
- อยู่ที่ไหน: หน้า checkpoint ของ plo_synthesis, `plo_report`, หรือทั้งสอง
- `plo_report` ตอนนี้บอกชื่อ Need ที่ไม่ถูกใช้อยู่แล้ว — ต่อยอดหรือทำใหม่

หลังทำเสร็จ เช็กว่าคำตอบทำให้ fog ข้อ "PLO report / มคอ.2 exporter ต้องรายงานไหม"
บนแผนที่ ชัดพอจะแตกเป็น ticket หรือยัง

**ผลลัพธ์**: mockup + คำตอบว่าโชว์ที่ไหน แสดงอะไร ลิงก์ไว้จาก ticket นี้

## เพิ่มหลัง ticket 02 ปิด

map มีสองแกนแล้ว → ก้อนที่ต้องโชว์อาจเป็น **สาม** ("แพ้ demand" / "นอกขอบเขต" /
"ไม่ใช่สมรรถนะบัณฑิต") ไม่ใช่สอง. [ticket 11](11-two-axis-selection.md) ข้อ 4 เป็นคนตัดสิน
ว่ายุบหรือไม่ยุบ — ใบนี้ออกแบบหน้าจอหลังจากรู้จำนวนก้อนแล้ว

และรายการในก้อน "ไม่ใช่สมรรถนะบัณฑิต" ต้องแสดงต่างจากก้อน "นอกขอบเขต": อย่างหลัง designer
ตัดสินว่า model อ่านสาขาถูกไหม อย่างแรกตัดสินว่าประโยคนั้นเขียนเป็น PLO ได้ไหมเลย

## Answer

**ก้อนเดียว ป้ายบอกเหตุผลรายรายการ** (ทางเลือก B จาก
[mockup](../checkpoint-mockup.html)) — ต่อยอด `UnusedNeeds` ที่ `PloReport.tsx`
ซึ่งมีอยู่แล้ว ไม่ทำหน้าใหม่

**1. ไม่แยกเป็นสามก้อน แม้จะตกลงไว้ตอนเปิดใบ**

[ticket 12](12-axis-overlap.md) วัดทีหลังว่าธงสองแกน**ทับกันเกือบทุกใบ** — หัวข้อ
"นอกสาขา" กับ "ไม่ใช่สมรรถนะบัณฑิต" จะลิสต์ Need ใบเดียวกันซ้ำสองที่เป็นเรื่องปกติ
ซึ่งตอนตัดสินว่า "สามก้อน" ยังไม่มีใครรู้. เหตุผลเดิมที่ว่า designer ต้องทำคนละอย่าง
กับแต่ละสาเหตุยังจริง แต่ป้ายบอกได้โดยไม่ต้องแยกก้อน และคงลำดับ demand ไว้ทั้งลิสต์

`exclusionReason()` derive จาก counter สองตัวบน `Need` — ไม่มี field ใหม่ ไม่มี
endpoint ใหม่ ป้ายที่แสดงคือ `นอกสาขา` / `ไม่ใช่สมรรถนะบัณฑิต` / `นอกขอบเขตหลักสูตร`
(ตกทั้งสองแกน) / `แพ้เพดาน`

**counter ที่หายไปแปลว่า "ผ่าน"** — `?? 1` ในฝั่ง UI สอดคล้องกับ default ของ model
และ backfill ของ migration: Need ที่เกิดก่อน guard ต้องอ่านเหมือนเดิมทุกประการ

**2. รายละเอียดอยู่หลังการกด ไม่ใช่แสดงตลอด**

การ**สแกน**ลิสต์ใช้ป้ายพอ แต่การ**ตัดสินว่าโมเดลอ่านผิดไหม**ต้องเห็นชื่อทักษะที่ทำให้
ถูกกันกับ `evidence_span_th`. แสดงตลอดจะทำให้ก้อนยาวจนกลบ Need ที่แพ้เพดาน
ซึ่งไม่ต้องอ่านเลย — ดึงจาก `/needs/{id}/trace` ตอนกด (แถวส่วนใหญ่ไม่เคยถูกเปิด)

**3. บล็อก "ต้องรันอะไรใหม่" อยู่ท้ายก้อน หนึ่งครั้งต่อหน้า**

เป็นคำสั่งระดับโปรแกรม ไม่ใช่ระดับ Need ใส่ทุกแถวคือพูดเรื่องเดียวกัน n ครั้ง
แสดงเฉพาะเมื่อมี Need ที่ถูกกันด้วย guard จริง

ถ้อยคำครอบสองทาง: **แก้ scope statement** (ลิงก์ไป Intake + บอกว่าต้องรันสกัดทักษะใหม่
ทั้งโปรแกรม และระบบไม่รันให้เอง) กับ **ยืนยันว่าอยากได้ทั้งที่นอกขอบเขต** (ลิงก์ไป
PLO Synthesis ซึ่งเป็นทาง override ทางเดียว)

**4. ป้ายสภาวิชาชีพ — มี**

การรัน eval จริงพบว่า guard กรอง Need ที่มีสมาชิกจากสภาวิชาชีพ 1-2 ใบต่อรอบ.
ป้ายนี้ไม่ผูกมัดคำตอบของ **จุดค้างข้อ 8** (`requirement` ควรข้าม guard ไหม):
ถ้าสุดท้ายตัดสินให้ข้าม ป้ายก็หายไปเองเพราะไม่มี Need แบบนั้นถูกกันอีก

เงื่อนไขใช้ `source_stakeholder_types.includes('professional_council')`
**ไม่ใช่** `classification_coverage.requirement` — อย่างหลังรวม
`institutional_direction` เข้ามาด้วย ซึ่งทำให้ป้ายที่เขียนว่า "สภาวิชาชีพระบุไว้" โกหก

**5. อยู่ที่ `plo_report` ที่เดียว**

หน้า PLO Synthesis ไม่ต้องแสดงซ้ำ — มันมีลิสต์ Need ทั้งหมดสำหรับเลือก merge อยู่แล้ว
และการเพิ่มก้อนที่สองที่นั่นจะทำให้ designer อ่านสองที่เพื่อเรื่องเดียวกัน

## ยืนยันจาก API จริง

รัน API กับ DB ที่ migrate แล้ว: `/needs/` คืน `in_field_skill_count`,
`graduate_capability_skill_count`, `source_stakeholder_types`, `member_skill_ids` ครบ
และ `/needs/{id}/trace` คืน `is_field_relevant` กับ `is_graduate_capability` รายทักษะ
— **ไม่ต้องแก้ API เลย** `Need` และ `ExtractedSkill` เต็มถูกส่งอยู่แล้ว

## ยังไม่ตัดสิน — ส่งต่อ

`plo_report` / มคอ.2 exporter ต้องรายงาน Need ที่ถูกกันไหม และรายงานให้ใคร
(designer อ่านเอง vs อยู่ในเอกสารที่ส่ง MHESI) — ใบนี้ตอบเฉพาะหน้าจอที่ designer อ่าน
`exporters/` ไม่ถูกแตะ ต้องเป็นใบใหม่

## แก้ข้อ 5 — 2026-09-28 · เพิ่มที่ checkpoint ของ need_combination ด้วย

ข้อ 5 เขียนว่า **"อยู่ที่ `plo_report` ที่เดียว"** และเหตุผลที่ให้ไว้คือหน้า PLO Synthesis
มีลิสต์ Need ทั้งหมดอยู่แล้ว การเพิ่มก้อนที่สองที่นั่นจะทำให้อ่านสองที่เพื่อเรื่องเดียวกัน

**เหตุผลนั้นยังถูก แต่ไม่ครอบหน้าที่เพิ่งเพิ่ม** — ตอนตัดสิน ใบนี้ตั้งตัวเลือกไว้สามทาง
("หน้า checkpoint ของ plo_synthesis, `plo_report`, หรือทั้งสอง") **checkpoint ของ
need_combination ไม่เคยอยู่ในตัวเลือก** ทั้งที่ตามกฎ immutable ข้อ 7 มันคือ checkpoint
**เดียว**ที่ชุด Need ถูกรีวิวก่อน synthesis จะรัน

สิ่งที่ทำให้มันคนละเรื่องกับหน้าอื่น คือ**ราคาของการแก้**:

| เห็นที่ไหน | ทางแก้ถ้า scope ตัดสินผิด | จ่ายอะไรไปแล้ว |
|---|---|---|
| checkpoint ของ need_combination | แก้ scope ที่ Intake → กด **Re-run Skill บนหน้านั้นเอง** | extraction 1 รอบ |
| `plo_report` (stage 6) | แก้ scope ที่ Intake → กลับไปรันใหม่ทั้งสาย | extraction + clustering + **synthesis ทุก call** + SMART loop |

รันจริงรอบล่าสุด: core PLO = 1 จากเกณฑ์ 6 และ scope guard คือตัวที่ตัดทิ้ง — designer
รู้เรื่องนี้ที่ stage 6

### สิ่งที่แสดง — ไม่ใช่ `UnusedNeeds` ทั้งก้อน

ที่ checkpoint **ไม่มีก้อน "แพ้เพดาน"** เพราะ demand ranking เกิดที่ synthesis ยังไม่เกิด
ตรงนี้ · เหลือแค่ in-scope กับไม่ · จึงเป็น

1. **ป้ายบนการ์ด** เมื่อ `scopeVerdict !== 'in_scope'` — ป้ายเดียวกับที่ report ใช้
   (`SCOPE_REASON_TH`) · `title` บอก counter ทั้งสองแกน
2. **ธงรายทักษะในแผง "ดูที่มา"** ที่มีอยู่แล้ว — `/needs/{id}/trace` คืน `ExtractedSkill`
   เต็มอยู่แล้ว ไม่แตะ API (ยืนยันไว้ในหัวข้อข้างบน)
3. **แถบสรุปหนึ่งแถบต่อหน้า** เมื่อมีใบถูกกัน — จำนวน + สองทางไปต่อ ตามข้อ 3 เดิม
   ต่างกันตรงปุ่มที่ต้องกดอยู่บนหน้านั้นเอง ไม่ใช่ส่งไปหน้าอื่น

**กาลของประโยคต่างกันและตั้งใจ** — report เขียน "ถูกกัน" (เกิดแล้ว) checkpoint เขียน
"**จะ**ไม่ถูกส่งต่อ" เพราะ `is_in_scope` ถูกเรียกที่ `plo_synthesis` ยังไม่มีอะไรตัดสิน
Need พวกนี้ตอนที่หน้านี้แสดงมัน

### กฎย้ายไป `frontend/src/constants/scope.ts`

`exclusionReason` กับ `SCOPE_PASS_RATIO = 0.5` เคยอยู่ใน `PloReport.tsx` ตอนที่มันเป็น
caller เดียว · สองหน้าเขียน 0.5 คนละที่คือวิธีที่สองหน้าจะเริ่มไม่ตรงกันว่า Need ใบไหนรอด
ซึ่งเป็น**ความผิดพลาดตัวเดียวกับที่ทำให้ใบ 07 ต้องเปิดใหม่** (eval เขียนเกณฑ์เองแล้วหลุด
จากของจริง)

`scopeVerdict` เป็นของกลาง ส่วน `lost_on_demand` อยู่ที่ `PloReport.tsx` ต่อไป — มีแต่
report ที่รู้ว่า Need ใบนั้นไม่มี PLO อ้างถึง

**ตรวจว่าตรงกับ Python จริง**: compile `scope.ts` แล้วรัน 294 เคส (member 0-8 × in_field
0-n × graduate 0-n รวมเคส counter หาย) เทียบกับ `passes_scope_axes` — **ไม่ตรงกัน 0 เคส**
ยังไม่มี test runner ฝั่ง frontend การตรวจนี้จึงเป็น manual ทำซ้ำได้ ไม่ใช่ CI
