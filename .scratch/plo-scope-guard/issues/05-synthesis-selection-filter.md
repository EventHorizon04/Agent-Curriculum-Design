# 05 — selection filter ใน plo_synthesis กับพฤติกรรมตอนต่ำกว่า MIN_NEEDS

Map: [PLO synthesis ที่ไม่หลุด scope ของหลักสูตร](../map.md)
Type: grilling
Status: resolved
Blocked by: 04 (resolved)

## Question

จุดกั้นจริงของ map นี้: `plo_synthesis` ข้าม Need นอกสาขาตอนเลือก — Need ยังถูกสร้าง
ยังถูกเก็บ ยัง trace ได้ (immutable rule 6) แค่ไม่ถูกหยิบไปร่าง PLO

ต้องตัดสิน:

1. **ตำแหน่งในโค้ด** — กรองก่อนหรือหลัง `synthesis_order()`? กรองก่อนแปลว่าลำดับ demand
   นับเฉพาะ Need ในสาขา ซึ่งเปลี่ยนเลข PLO1..PLOn ที่ designer เห็น
2. **ครอบ OPT ด้วย** — ตกลงแล้วว่า optional PLO ก็กรอง (นอกสาขาก็คือนอกสาขา ไม่ว่าหลักหรือเสริม)
   ยืนยันว่าไม่มีเส้นทางอื่นที่ Need นอกสาขาเข้าเป็น PLO ได้ — ไล่ทุก caller ของ
   `synthesize_from_needs`
3. **ต่ำกว่า `MIN_NEEDS` (6)** — กรองต่อ + log policy warning ไม่เติมของนอกสาขาให้ครบโควตา
   ถ้อยคำ warning ต้องบอกอะไรบ้างเพื่อให้ designer แยกออกว่า "evidence ในสาขาไม่พอ"
   ต่างจาก "Need น้อยแต่เดิม" ที่ `need_combination.py:320` เตือนอยู่แล้ว — สองอันนี้
   ต้องไม่อ่านเหมือนกัน
4. **`POST /plos/from-needs` (merge route) ไม่กัน** — ตกลงแล้วว่าปล่อย เพราะ designer
   เลือกเองคือการตัดสินใจของคน ไม่ใช่ของ pipeline. ยืนยันว่าไม่ต้อง warn ใน response ด้วย
   และเขียนเหตุผลลง spec ให้ชัดว่าเป็นเจตนา ไม่ใช่ช่องที่ลืมปิด — พร้อมบอกว่านี่คือทาง
   override เพียงทางเดียว (จึงไม่ต้องมีปุ่ม override แยก)
5. **`POST /plos/from-needs` ตรวจ `MIN_NEEDS` / `MAX_CORE_PLOS` อยู่แล้ว** — การกรองทำให้
   จำนวน Need ที่ระบบเลือกได้ลดลง ต้องดูว่าเงื่อนไข refuse เดิมยังอ่านถูกไหมเมื่อ core count
   ตั้งต้นต่ำกว่าเดิม

**ขอบเขต**: ตัดสินใจอย่างเดียว ผลลงเป็นหัวข้อใน spec

## Answer

**ลำดับใหม่ใน `plo_synthesis.run()`**

```
needs → [filter: is_in_scope] → แยก optional → synthesis_order → ceiling → loop
```

**1. กรองก่อน `synthesis_order` และสำคัญกว่านั้นคือ ก่อน `MAX_CORE_PLOS`**
กรองหลังเพดานจะทำให้เพดานหยิบ 10 ใบแรกที่มีนอกขอบเขตปนอยู่ แล้วกรองทิ้งเหลือ 7 PLO
ทั้งที่ยังมี Need ในขอบเขตอีกหลายใบรออยู่ท้ายแถว — เพดานต้องนับเฉพาะใบที่มีสิทธิ์

**ไม่ข้ามตอน loop เพื่อเว้นเลข**: ช่องว่างของเลข PLO มีความหมายอยู่แล้วว่า
"Need ใบนี้ร่างไม่สำเร็จ" (`plo_synthesis.py:379`) ใส่ความหมายที่สองเข้าไปทำให้อ่านไม่ออก
ทั้งคู่. Need ที่ถูกกรองอยู่สถานะเดียวกับ Need ที่แพ้เพดาน — **ไม่ถูกเลือก ไม่ใช่พัง** —
และเพดานก็ไม่กินเลข

**2. ใบนี้ตรึงโครง ไม่ตัดสินเกณฑ์** — นิยาม predicate เดียว `is_in_scope(need) -> bool`
เรียกที่เดียว. เนื้อในเป็นของ [ticket 11](11-two-axis-selection.md) เพราะยังไม่มีข้อมูล
พอจะเลือก `and`/`or`: เพดานสองแกนคือ ~50% กับ 56% และ**ยังไม่รู้ว่าพลาดคนละใบหรือใบเดียวกัน**
ซึ่งเปลี่ยนคำตอบทั้งหมด (`and` บนสัญญาณที่พลาดคนละใบ = กรองแรงเกิน) — ของที่
[ticket 07](07-eval-protocol.md) ต้องวัด. ไม่ว่ากฎออกมาแบบไหน ตำแหน่งเรียกไม่เปลี่ยน

**3. predicate อยู่ที่ `need_grouping.py` ข้าง `MIN_NEEDS` / `MAX_CORE_PLOS`**
โมดูลนั้นมีเหตุผลกำกับอยู่แล้วว่าทำไม policy ถึงอยู่ตรงนั้น และ predicate นี้คือ policy
ตัวที่สามที่ตัดสิน**ว่า Need ไหนได้เป็น PLO** เหมือนกันเป๊ะกับสองค่าเดิม. วางที่
`plo_synthesis` จะทำให้ policy กระจายสองที่โดยไม่มีเส้นแบ่งที่อธิบายได้; โมดูล
`scope_guard.py` แยกยังไม่คุ้มจนกว่า ticket 07 จะพาให้เกิด threshold หลายตัว

**4. ถ้อยคำตอนเหลือต่ำกว่า `MIN_NEEDS`** — log บรรทัดแยกตอนกรอง (กี่ใบ ชื่ออะไร)
**และเติมสาเหตุเข้าไปใน warning `MIN_NEEDS` เดิม** (`plo_synthesis.py:383`)
designer ต้องแยก "evidence ในสาขาไม่พอ" ออกจาก "Need น้อยแต่เดิม"
(`need_combination.py:320`) ให้ได้ — สองอย่างนี้อ่านต่างกันได้ก็ต่อเมื่อบรรทัดที่บอกว่า
ต่ำกว่า 6 บอกสาเหตุมาในบรรทัดเดียวกัน ไม่ใช่ให้คนอ่านต่อเอาเองจากสองบรรทัดคนละที่ในล็อก

**5. merge route (`POST /plos/from-needs`) — ไม่กรอง log อย่างเดียว ไม่แตะ floor check**
- **ไม่กรอง โดยเจตนา**: designer เลือก Need เองคือการตัดสินใจของคน ไม่ใช่ของ pipeline
  และนี่คือ**ทาง override เพียงทางเดียว** จึงไม่ต้องมีปุ่ม override แยก (ตรงกับที่
  map ระบุไว้ใน Out of scope)
- **`logger.warning` เมื่อ Need ที่เลือกอยู่นอกขอบเขต ไม่ warn ใน response**:
  response ที่เตือนคือการทวงถามการตัดสินใจที่คนเพิ่งตัดไปแล้ว แต่ต้องตามรอยได้ว่า
  PLO นอกขอบเขตข้อนี้มาจากไหน — แบบเดียวกับบรรทัด `released` ที่มีอยู่แล้ว
- **floor check ไม่ต้องแก้**: `projected_core < MIN_NEEDS and projected_core < current_core`
  กันเคสนี้ไว้แล้ว — โปรแกรมที่การกรองทำให้เหลือ 4 PLO จะไม่ถูกปฏิเสธทุก merge ต่อจากนั้น
  เพราะเงื่อนไขที่สองบังคับว่า merge นี้ต้องเป็นตัวที่ทำให้ลดลง เจตนาเดิมตรงกับที่ต้องการพอดี

## ยืนยันจากโค้ด (ไม่ใช่ข้อตัดสิน)

- **ไม่มีเส้นทางอื่นที่ Need นอกขอบเขตเข้าเป็น PLO** — `synthesize_from_needs` มี caller
  สองที่เท่านั้น: `plo_synthesis.run()` และ `api/routes/plos.py:291`. optional series
  ใช้ `synthesis_order` ตัวเดียวกัน วาง predicate ก่อน `for is_optional in (False, True)`
  ครอบทั้งสองซีรีส์ — **นอกสาขาก็คือนอกสาขา ไม่ว่าหลักหรือเสริม**
- **ห้ามเพิ่ม branch "โปรแกรมนี้มี scope statement ไหม"** — โปรแกรมที่ไม่มี scope statement
  มีธงเป็น `True` ทุกแถวจาก default ของ [ticket 04](04-two-axis-flags-on-need.md)
  → counter = total → predicate ผ่านหมด → **กลายเป็น no-op เอง**. ข้อนี้ต้องอยู่ใน spec
  เพราะคนถัดไปจะเพิ่ม branch นั้นเข้ามาโดยคิดว่ามันหลุด
- **`plo_report` ไม่แก้ในใบนี้** — Need ที่ถูกกรองรวมอยู่กับ "unused Needs" ที่มีอยู่แล้ว
  ส่วนจะแยกเป็นสองถังไหมคือ [ticket 06](06-checkpoint-two-buckets.md)
