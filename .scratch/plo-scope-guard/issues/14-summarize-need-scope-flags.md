# 14 — `summarize_need` ควรเห็นธง scope รายสมาชิกไหม และถ้าเห็นควรทำอะไร

Map: [PLO synthesis ที่ไม่หลุด scope ของหลักสูตร](../map.md)
Type: grilling
Status: open
Blocked by: (none)

## Question

สองแกนถูกอ่านที่ **selection** (`is_in_scope` กรอง Need ทั้งใบก่อน `plo_synthesis` เลือก)
แต่ไม่มีใครอ่านมันตอน **เขียนประโยค Need**. `build_summarize_need_prompt` รับ
`skill_names` กับ `ksec`/`bloom_level` และ `program_context` เท่านั้น — ไม่รู้ว่าสมาชิก
คนไหนติดธง และ `_Group` ก็เก็บมาเฉพาะ **counter** สองตัว (`in_field_skill_count`,
`graduate_capability_skill_count`) ไม่ใช่ธงรายตัว ทั้งที่ `_build_groups` ถือ
`ExtractedSkill` รายตัวอยู่ในมือตรงนั้น

ใบนี้ต้องตัดสินสองชั้น:

1. **ควรเห็นไหม** — หรือปล่อยให้ selection เป็นที่เดียวที่อ่านธง
2. **ถ้าเห็น ควรทำอะไร** — สามรูปที่ต่างกันจริง:
   - **(ก) ข้ามทักษะที่ติดธง**: ส่งเฉพาะชื่อที่ผ่านทั้งสองแกนเข้า `keywords`
   - **(ข) บอกโมเดลว่าตัวไหนติดธง แล้วให้มันกันออกเอง** ในประโยคที่เขียน
   - **(ค) เขียนใหม่แบบ T3 ของ [ticket 09](09-graduate-capability-prompt.md)** — แปลงข้อ
     เรียกร้องฝั่งสถาบันเป็นฝั่งบัณฑิตเมื่อแปลงได้ ("ต้องการหลักสูตรที่ผสาน AI" →
     "ใช้ AI ในงานแปลได้")

## ทำไมใบนี้เกิดขึ้นที่นี่ ไม่ใช่ที่ชั้นสกัด

[ticket 09](09-graduate-capability-prompt.md) วัด T3 (เขียนใหม่) ที่ `extract_skills` แล้ว
**ตัดออก**: เขียนใหม่ 45 ครั้งทำให้ชื่อทักษะไม่ตรงกับ `evidence_span_th` ที่ต้องคัดลอก
ตรงตัว = ชน immutable rule 2. ข้อจำกัดนั้น **ไม่มีที่ระดับ Need** — `Need` ไม่มี span,
`source_evidence_ids` มาจากสมาชิก และสมาชิกยังคงชี้กลับหลักฐานเดิมได้ไม่ว่าประโยคจะเขียน
ว่าอะไร ticket 09 จึงระบุเองว่า "ที่ทางของการเขียนใหม่คือ `summarize_need`"

**หลักฐานว่ามนุษย์ทำที่ระดับนี้จริง**: `Needs_to_PLO_TCISM.xlsx` เก็บ Need ของผู้บริหาร (9),
อ.ผู้รับผิดชอบ (10), อ.ผู้สอน (11) ไว้ครบทั้งสามใบ **แล้วเขียนใหม่** ไม่ได้ทิ้ง —
ตรงกับที่ [ticket 04](04-two-axis-flags-on-need.md) ข้อ 7 ห้ามตัดที่ระดับ stakeholder

## สิ่งที่ต้องกดให้แตกก่อนตอบ

1. **Need ที่การเขียนใหม่จะช่วย มีจำนวนเท่าไร** — `SCOPE_PASS_RATIO = 0.5` กรอง Need ที่
   สมาชิกติดธงเกินครึ่งออกไปแล้ว ใบที่เหลือให้ summarize เห็นคือใบที่ **ติดธงน้อยกว่าครึ่ง**
   ปนอยู่ ถ้าบนผลรัน 10 Need ของ TCISM มีแค่ใบเดียวสองใบ ต้นทุนของ (ก)/(ข)/(ค) อาจแพงกว่าผล
   **วัดจากข้อมูลที่เก็บไว้แล้วได้ ไม่ต้องเรียก LLM ใหม่** เหมือนที่
   [ticket 12](12-axis-overlap.md) ทำ
2. **(ก) ขัดกับ traceability หรือไม่** — ถ้าประโยคเขียนจาก subset แต่
   `Need.source_evidence_ids` ยังรวมหลักฐานของสมาชิกที่ถูกข้าม PLO ที่ได้จะอ้างหลักฐานที่
   ประโยคไม่ได้พูดถึงเลย นั่นคือ trail ที่ผ่าน validator แต่โกหก (รูปเดียวกับบั๊ก
   `source_evidence_ids` ปลอมที่ whole-branch review จับได้ตอน need-based restructure)
   — ทางแก้ที่เป็นไปได้: ตัดสมาชิกที่ติดธงออกจากกลุ่มไปเลย ไม่ใช่แค่จากประโยค
   ซึ่งเปลี่ยนจาก "เขียนประโยค" เป็น "แก้การจัดกลุ่ม" และไปแตะสิ่งที่ map ประกาศไม่แตะ
3. **(ค) ทำให้ประโยคเป็น PLO เสร็จรูปหรือไม่** — กติกาปัจจุบันห้าม
   "บัณฑิตวิเคราะห์...ได้" เพราะ `plo_synthesis` ได้รับเฉพาะประโยคนี้ การ "แปลงฝั่งสถาบัน
   เป็นฝั่งบัณฑิต" คือการเขียนสิ่งที่บัณฑิตทำได้ ซึ่งเดินเข้าหาเส้นนั้นตรง ๆ
   ถ้าเลือก (ค) ต้องบอกให้ได้ว่าเส้นแบ่ง "ข้อกำหนด vs ผลลัพธ์" ยังอยู่ตรงไหน
4. **recall 56% พอให้ทำอะไรอัตโนมัติไหม** — [ticket 04](04-two-axis-flags-on-need.md) ข้อ 4
   ปฏิเสธ majority ด้วยเหตุนี้ ถ้าเชื่อธงไม่ได้ครึ่ง การให้ prompt ทำตามธงคือการทำตาม
   สัญญาณที่พลาดครึ่ง — (ข) เจ็บน้อยสุดเพราะโมเดลยังใช้วิจารณญาณ, (ก) เจ็บสุด
5. **ต้นทุน cache = ศูนย์** ต่างจาก [ticket 03](03-extraction-prompt-and-cache.md):
   `complete_light(_NeedStatement, build_summarize_need_prompt(...))` **ไม่ผ่าน `llm_cache`
   เลย** (มีแต่ `llm_clustering` กับ `skill_extraction` ที่ผ่าน) เปลี่ยน prompt นี้จึงไม่
   ทำให้แถวไหนตาย — ข้อคัดค้านเรื่องราคาที่คุมทางเลือกในใบ 03 ใช้ที่นี่ไม่ได้
6. **`test_summarize_need.py` pin อะไรไว้แล้ว** — เส้นแบ่ง "Need ไม่ใช่ PLO เสร็จรูป"
   ถูกตรึงไว้ที่นั่น ทางเลือกที่เลือกต้องไม่ทำให้ test นั้นต้องผ่อน

## ขอบเขต
