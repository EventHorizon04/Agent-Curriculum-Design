## Question

1. **หลักสูตรตัวอย่างกี่อัน อะไรบ้าง** — เสนอไว้ 3 (พยาบาล / วิศวะ / บริหาร) เพราะขอบสาขา

   พอสำหรับ 3 สาขาไหม หรือต้อง scrape เพิ่ม
3. **"PLO นอกสาขา" นับยังไง** — ใครตัดสิน คน หรือ LLM judge? ถ้าเป็นคน ต้องมี rubric
   ที่คนละคนอ่านแล้วให้ผลตรงกัน. ถ้าเป็น LLM ก็คือถามคำถามเดียวกับที่ระบบเพิ่งตอบ

4. **baseline** — วัด "ก่อน" ยังไงในเมื่อ scope statement ยังไม่มี? รันด้วย branch เดิม

5. **เกณฑ์ผ่าน** — ตัวเลขอะไรถึงเรียกว่าสำเร็จ และถ้าไม่ผ่าน ผลนั้นส่งกลับไปที่ไหน
   (fog ข้อ "ถ้า `is_field_relevant` ไม่แม่นพอ จะเชื่ออะไรแทน")

**ขอบเขต**: ออกแบบ protocol ลง spec — **ไม่รัน eval**. การรันต้องรอ implementation
ซึ่งอยู่หลัง destination ของ map นี้

## Answer

### ชุดข้อมูล

**สองเคส: TCISM ของจริง + เคสสังเคราะห์ที่ต่อยอดจากมัน**

1. **TCISM ล้วน** — evidence 14 รายการ เฉลยจาก `Needs_to_PLO_TCISM.xlsx`
   วัดแกน **"ไม่ใช่สมรรถนะบัณฑิต"** เป็นหลัก (CORE: ev06-09, ev14 · NOISE: ev10, ev11)
2. **TCISM + evidence ยัด** — job posting จากสาขาอื่นไปเลย (วิศวะ/พยาบาล จาก
   `Data/linkedin_offers2026-04-30.csv`) วัดแกน **"นอกสาขา"** ซึ่ง TCISM ล้วนไม่มีเคส
   (evidence ของ TCISM ทุกชิ้นอยู่ในสาขา — มนุษย์เก็บ theme D ผู้ประกอบการไว้เป็น PLO4 ด้วยซ้ำ)

**เฉลยของเคสสังเคราะห์รู้แน่นอนโดยการก่อสร้าง** — ไม่มี rubric ให้คนละคนอ่านแล้วเถียงกัน
และไม่มี LLM judge ที่ถามคำถามเดียวกับที่ระบบเพิ่งตอบ ซึ่งเป็นสองทางตันที่ใบนี้ตั้งไว้แต่แรก

**stakeholder_type ของ evidence ที่ยัด: ทั้ง `employer` และ `professional_council`
รายงานแยกสองก้อน** — "requirement wins" เป็นกฎที่**ตั้งใจให้ guard กรองไม่ได้**
ถ้า eval ไม่มีเคสนั้น คนอ่านผลจะเห็นมันเป็น false negative แล้วไป "แก้" กฎที่ทำงานถูกอยู่
รายงานต้องมีบรรทัดว่า *"กรองไม่ได้ N ใบ เพราะเป็น requirement — ถูกต้องตามนโยบาย"*

**ยังไม่ต้องมีหลักสูตรที่สาม** — สิ่งที่ทำให้เคสใช้ได้คือเฉลยของมนุษย์ ซึ่งขอจากมหาวิทยาลัย
ไม่ได้ตามใจ. ผูก map ไว้กับงานที่เราสั่งไม่ได้คือการบล็อกตัวเอง

### ระดับที่วัด

**ระดับ Need เป็นตัวตั้งเกณฑ์ ระดับ skill เป็น diagnostic**

กฎ any ของ [ticket 04](04-two-axis-flags-on-need.md) ขยายผลไปในทางที่ทำให้ตัวเลข skill
**หลอก**: Need ที่มีสมาชิก 8 ตัวถูกกรองก็ต่อเมื่อ **ทั้ง 8 ตัว** ติดธง — recall 56%
ที่ระดับ skill จึงกลายเป็นตัวเลขที่ต่ำกว่านั้นมากที่ระดับ Need และนั่นคือตัวที่ตัดสินว่า
PLO หลุดหรือไม่

**ไม่วัดที่ระดับ PLO** — ต้องจ่ายค่า synthesis ทุกรอบเพื่อวัดสิ่งที่ระดับ Need ตัดสินไปแล้ว
PLO ที่หลุดคือ PLO ที่ Need หลุดผ่านมา ไม่มีทางหลุดเพิ่มที่ชั้นนั้น

### เกณฑ์ผ่าน — asymmetric

- **hard gate: `FP = 0` ที่ระดับ Need** (Need ในสาขาต้องไม่ถูกกรองแม้ใบเดียว)
- **recall: รายงานเทียบ baseline ไม่ใช่ gate**

สองฝั่งไม่เท่ากันในผลที่ตามมา: Need ในสาขาที่ถูกกรองผิดคือ **PLO ที่หายไปจากหลักสูตร
โดยไม่มีใครรู้** ส่วน Need นอกสาขาที่หลุดเข้ามาคือของที่ designer เห็นที่ checkpoint
([ticket 06](06-checkpoint-two-buckets.md)) แล้วลบได้ในสามวินาที. เกณฑ์เดียวที่บีบทั้งสองฝั่ง
เข้าเลขเดียวคือการแลกของที่กู้คืนไม่ได้กับของที่กู้คืนได้

**ตัวเลข recall ตายตัวตั้งไม่ได้ตอนนี้** — ไม่มีใครวัด recall ที่ระดับ Need มาก่อน

### baseline — สองตัว

| | คือ | ตอบคำถาม |
|---|---|---|
| `B0` | branch เดิม ก่อนธงใหม่ | — |
| `B1` | branch ใหม่ scope ว่าง | `B1 − B0` = **ช่องธงที่สองให้อะไร** |
| ผลจริง | branch ใหม่ + scope | `ผล − B1` = **scope statement ให้อะไร** |

**ประโยคเดิมในใบนี้ที่ว่า "ไม่มี scope = พฤติกรรมเดิมเป๊ะ และนั่นเป็น test ในตัว"
ใช้ไม่ได้อีกแล้ว** — [ticket 12](12-axis-overlap.md) วัดว่าการเพิ่มช่อง
`is_graduate_capability` ดันธงสาขาจาก 3/9 เป็น 5/9 ทั้งที่ไม่มี scope เลย.
ยังจริงที่ระดับ **prompt bytes ของบรรทัด scope** (บรรทัดนั้นไม่มีจริง ๆ) แต่ไม่จริง
ที่ระดับผลลัพธ์ — และ `B1 − B0` คือตัวเลขที่ต้องดูวันที่ตัดสินใจว่าจะยุบเป็นแกนเดียวไหม

### metric ที่รายงานทุกรอบ

1. recall / FP ที่ระดับ **Need** แยกสองแกน และรวม
2. recall / FP ที่ระดับ **skill** (diagnostic — อธิบายว่าทำไมตัวเลข Need ออกมาแบบนั้น)
3. **overlap ของสองแกน** (ตาราง 2×2 แบบ [ticket 12](12-axis-overlap.md)) — ตัวที่ตัดสินว่า
   เก็บสองคอลัมน์ไว้ถาวรคุ้มไหม
4. **contamination** — ทักษะที่ชื่อหรือ span ลอกวลีจาก scope statement
   ([ticket 13](13-scope-position.md)) เป็น metric **ถาวร** ไม่ใช่วัดครั้งเดียวแล้วเลิก
   เพราะยังไม่รู้ว่า scope ที่ยาวกว่า ~150 ตัวอักษรจะเริ่มปนไหม
5. จำนวนที่ **กรองไม่ได้เพราะ requirement wins** — พร้อมคำกำกับว่าถูกต้องตามนโยบาย

### ถ้าไม่ผ่าน — fallback ที่ประกาศไว้ล่วงหน้า

**ปิดสวิตช์กรอง เหลือแต่ติดธงให้ designer ดูที่ checkpoint**

[ticket 06](06-checkpoint-two-buckets.md) สร้างหน้าที่แสดง Need ที่ถูกกันอยู่แล้ว
การถอยจึงเป็นการ**ปิดการกรองอัตโนมัติ** ไม่ใช่เขียนอะไรใหม่ — degradation ที่ถูกที่สุด
ที่ map นี้จะมีได้ และเป็นเหตุผลเพิ่มที่ `is_in_scope()` ต้องเป็น predicate เดียว
เรียกที่เดียว ([ticket 05](05-synthesis-selection-filter.md))

การปรับถ้อยคำ prompt แล้ววัดใหม่ทำได้ระหว่างทางอยู่แล้ว ไม่ต้องประกาศเป็น fallback
ส่วน "หาสัญญาณอื่นแทนธงจากโมเดล" เป็นงานวิจัยเปิดที่ไม่ควรผูกกับเงื่อนไข "ถ้า eval ไม่ผ่าน"

### รันเมื่อไหร่

**manual — สคริปต์ใน `scripts/` รันเมื่อแตะ prompt, เปลี่ยน model, หรือย้าย slot**
ไม่ใช่ CI: มันเรียก LLM จริง 28-70 call ต่อรอบ จะจ่ายทุกครั้งที่มีคนแก้ typo
และผลไม่ deterministic พอจะเป็น gate สีแดง/เขียว

สิ่งที่อยู่ใน CI คือ unit test ของ `is_in_scope()` และ cache key ซึ่ง deterministic ล้วน
**eval เป็นเครื่องมือตัดสินใจของคน ไม่ใช่ด่านอัตโนมัติ** — ผลเก็บเป็นไฟล์ที่ commit ไว้
เทียบข้ามรอบได้

### ผลกระทบของการยัด evidence ต่อ `demand_score`

`demand_score` = `0.30 × mandate + 0.70 × share of corpus` — ยัด evidence เข้าคลังแล้ว
ทุก Need เดิมได้คะแนนใหม่ **แต่ไม่กระทบ metric ของ guard เลย**: [ticket 05](05-synthesis-selection-filter.md)
ตัดสินให้กรอง**ก่อน** `synthesis_order` จึงอยู่ก่อนจุดที่ `demand_score` เข้ามาเกี่ยว

- **เทียบข้ามเคสได้**: recall / FP ที่ระดับ Need
- **เทียบไม่ได้ และไม่ต้องเทียบ**: "Need ไหนได้เป็น PLO"

ไม่ตรึง corpus size ด้วยการเอา evidence ของ TCISM ออก — นั่นคือเปลี่ยนโจทย์เพื่อให้เลขสวย

## แก้หลังรัน eval จริง — ใบนี้เขียนเรื่อง `requirement` ผิด

Answer ข้างบนเขียนว่า *"requirement wins เป็นกฎที่**ตั้งใจให้ guard กรองไม่ได้**"*
และให้รายงานว่า *"กรองไม่ได้ N ใบ เพราะเป็น requirement — ถูกต้องตามนโยบาย"* — **ผิดทั้งคู่**

`requirement wins` ตัดสิน **`classification` เท่านั้น** (`classify_skills` กฎ 1-2 ทับกฎ 3
ที่ว่า off-field → `unclassified`) ส่วน `is_in_scope()` อ่าน counter บน `Need` ซึ่งนับจาก
**ธงดิบรายแถว** — `classification` ไม่เคยไปถึงมัน. ทักษะที่สภาวิชาชีพสั่งแล้วโมเดลตีว่า
นอกสาขาจึงถูกกรองเหมือนของอื่นทุกประการ

ที่มาของความผิด: ใบนี้ยกกฎ "requirement wins" มาจาก
[ticket 04](04-two-axis-flags-on-need.md) ข้อ 5 ซึ่งพูดถึงมันในบริบทของ `classification`
ล้วน ๆ (และถูกต้องในบริบทนั้น) แล้วอนุมานต่อเองว่ามันปกป้องการกรองด้วย โดยไม่มีใครไล่
เส้นทางจาก `classification` ไปถึง `is_in_scope` — ซึ่งไม่มีเส้นทางนั้น

การรัน `scripts/eval_scope_guard.py` ยืนยันเชิงประจักษ์: **1-2 Need ต่อรอบถูกกรอง
ทั้งที่มีสมาชิก `classification=requirement`**

**metric ข้อ 5 จึงกลับด้าน** — ไม่ใช่ "กรองไม่ได้เพราะเป็น requirement" แต่เป็น
"**กรองไป** N ใบ ทั้งที่มีสมาชิกเป็น requirement" ซึ่งเป็นสัญญาณเตือน ไม่ใช่การยืนยัน
ว่ากฎทำงานถูก. เหตุผลที่ยังต้องยัด `professional_council` เข้าเคสสังเคราะห์คือการ
**วัดขนาดของช่องนี้**

**คำถามใหม่ที่ไม่มีใบไหนรับผิดชอบ**: `requirement` ควรข้าม `is_in_scope` ไหม
(ก) ปล่อยตามนี้ (ข) ให้ข้ามเหมือนที่มันข้าม `unclassified` อยู่แล้ว
(ค) ไม่ข้าม แต่ยกเป็นก้อนแยกที่ checkpoint ให้ designer ตัดสินก่อนเสมอ
