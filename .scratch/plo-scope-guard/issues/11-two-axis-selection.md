## Question

[ticket 05](05-synthesis-selection-filter.md) วางกลไกกรองไว้บนแกนเดียว ("อยู่ในสาขาไหม")
ตอนนี้มีสองแกน ใบนี้ตัดสินว่ามันประกอบกันยังไงที่จุดเลือก Need

ต้องตัดสิน:

1. **AND หรือคนละชั้น** — Need ต้องผ่านทั้งสองแกนถึงได้เป็น PLO ใช่ไหม และถ้าตกคนละแกน
   ผลต่างกันไหม? ตกแกน "ไม่ใช่บัณฑิต" หนักกว่าตกแกน "นอกสาขา" — อย่างหลังยังเป็นความต้องการ
   ของตลาดที่หลักสูตรเลือกไม่ตอบ ส่วนอย่างแรกเป็นประโยคที่เขียนเป็น PLO ไม่ได้เลย
2. **ลำดับการกรอง** — กรองแกน "ไม่ใช่บัณฑิต" ก่อนแล้วค่อยแกนสาขา หรือพร้อมกัน? มีผลต่อ
   ตัวเลขที่ policy warning รายงาน และต่อเลข PLO1..PLOn ที่ designer เห็น
3. **`MIN_NEEDS` เมื่อกรองสองชั้น** — [ticket 05](05-synthesis-selection-filter.md)
   ตกลงไว้ว่ากรองต่อแล้ว log warning ไม่เติมของนอกสาขาให้ครบโควตา. สองชั้นทำให้ตกต่ำกว่า 6
   ง่ายขึ้นมาก — และเฉลยมนุษย์ของ TCISM มี **4 PLO** ซึ่งต่ำกว่าพื้นอยู่แล้ว.
   ยืนยันว่ายังกรองต่อ และ warning ต้องแยกได้ว่าขาดเพราะแกนไหน
4. **ก้อนที่โชว์ที่ checkpoint** — [ticket 06](06-checkpoint-two-buckets.md) ออกแบบไว้
   สองก้อน ("แพ้ demand" / "นอกขอบเขต") ตอนนี้เป็นสาม. ยืนยันว่าสามก้อนยังอ่านไหว
   หรือควรยุบสองก้อนหลังเป็น "ถูกกัน" ก้อนเดียวพร้อมเหตุผลต่อรายการ
5. **merge route** — [ticket 05](05-synthesis-selection-filter.md) ตกลงว่า
   `POST /plos/from-needs` ไม่กันแกนสาขา เพราะ designer เลือกเองคือการตัดสินใจของคน.
   แกนใหม่เหมือนกันไหม? "บัณฑิตบริหารทรัพยากรอย่างมีประสิทธิภาพ" เป็น PLO ที่ผิดรูป
   ไม่ใช่แค่ผิดสาขา — อาจเป็นจุดที่ควรกันแม้คนสั่ง

**ขอบเขต**: ตัดสินใจอย่างเดียว ผลลงเป็นหัวข้อใน spec

## เพิ่มหลัง ticket 12 ปิด — โจทย์เปลี่ยน

[ticket 12](12-axis-overlap.md) วัดแล้วว่าสองแกน**ทับกัน 100%**: ไม่มีทักษะตัวใดติดธง
แกนเดียว `and` กับ `or` จึงให้ตัวเลขเท่ากันเป๊ะ — **เลือกจากข้อมูลไม่ได้**

ต้องตัดสินใหม่:

1. **`and`/`or` ตัดสินจากเหตุผลเชิงนโยบายแทน** — ข้อมูลชี้ไปทาง `or`: กฎ any ที่ระดับ
   skill (ticket 04) เป็นฝั่งปล่อยผ่านอยู่แล้ว การซ้อน `and` ที่ระดับ Need จะกรอง
   แทบไม่ได้อะไรเลย. แต่ต้องเขียนเหตุผลไว้ว่าทำไมไม่ใช่ `and`
2. **เก็บสองธงแยกยังคุ้มไหม** — ticket 04 ตัดสินให้แยกด้วยเหตุผลเชิงแนวคิด
   ("การสร้างเครือข่ายความร่วมมือระดับสากล" in-field แต่ไม่ใช่สมรรถนะบัณฑิต)
   แต่ข้อมูลบอกว่า**โมเดลไม่ได้แยกแบบนั้น** — มันตั้งธงสาขาให้ตัวนั้นเป็น false ไปด้วย.
   ยุบเป็นแกนเดียวจะเสียอะไร และถ้าไม่ยุบ ต้องทำอะไรให้มันแยกกันจริง
   (prompt ที่ถามสองคำถามแยกกัน? นิยามที่คมกว่า?)
3. **ตัวอย่างเล็กเกินจะปิดคำถาม** — NOISE ทั้งชุดมี 9 ทักษะจาก evidence 2 รายการ.
   ต้องตัดสินว่าจะตัดสินตอนนี้เลย หรือรอ [ticket 07](07-eval-protocol.md) วัดบนชุดที่ใหญ่กว่า

## Answer

**1. เก็บสองธงแยกไว้ selection ใช้ `or`** — Need ตกแกนใดแกนหนึ่งก็ถูกกัน
`is_in_scope(need)` = `in_field_skill_count > 0 and graduate_capability_skill_count > 0`
(ผ่านต้องผ่านทั้งคู่ = ถูกกันเมื่อ OFF แกนใดแกนหนึ่ง)

**เหตุผลที่ไม่ยุบเป็นแกนเดียว ไม่ใช่ "เผื่อไว้" แต่มาจากตัวเลขของ
[ticket 12](12-axis-overlap.md) เอง**: การเพิ่มช่อง `is_graduate_capability`
ดันธงสาขาจาก 3/9 เป็น 5/9 ทั้งที่ไม่มี scope statement เลย — **ช่องที่สองมีมูลค่า
แม้จะตอบซ้ำ** ลบออกอาจเสีย recall กลับไปที่ control. ธงเดียวที่มีนิยามรวมสองเกณฑ์
อาจให้ 5/9 เท่าเดิมหรืออาจกลับไป 3/9 — **ไม่มีใครวัด ยุบตอนนี้คือเดา**

**ไม่เก็บธงแล้วไม่ใช้** (แกนบัณฑิตไว้โชว์เฉย ๆ) — ถ้าไม่ใช้ก็ไม่ต่างจากไม่มี

**2. merge route ไม่กันทั้งสองแกน** — เส้นเดียวกับ
[ticket 05](05-synthesis-selection-filter.md) log อย่างเดียว ไม่ 422 ไม่ warn ใน response

เรียงตามน้ำหนัก:
- ticket 12 วัดว่าธง grad-OFF **ไม่เคยมาเดี่ยว** (0 ตัวจาก 38) ทุกตัวติดคู่กับธงสาขา
  → การกันแกนบัณฑิตคือการกันของชิ้นเดียวกับที่แกนสาขาปล่อยผ่านอยู่ = นโยบายขัดกันเอง
  บน request เดียว
- PLO ที่ผิดรูปมีด่านของมันอยู่แล้ว: SMART hard check กับ soft judge จับ
  "บริหารทรัพยากร" ที่เขียนเป็น PLO ได้ตรงกว่าธงที่ตัดสินตั้งแต่ชั้นสกัด
- recall 56% แปลว่าอีก 44% ธงไม่ติดทั้งที่ควรติด — 422 บนสัญญาณครึ่งใบจะบล็อกงาน
  ที่ถูกต้องของ designer โดยไม่มีทางออก

**3. `is_in_scope()` คืน `bool` เท่านั้น — เหตุผลมาจาก counter** ที่
[ticket 04](04-two-axis-flags-on-need.md) เก็บไว้บน `Need` แล้ว: ตัวไหนเป็น 0
คือแกนนั้นที่ทำให้ตก. ได้เหตุผลฟรีและละเอียดกว่า enum ("0 ใน 8" ไม่ใช่แค่ `off_field`)
enum ที่เก็บลง Need จะเป็นข้อมูลซ้ำที่ไม่มีวันตรงกันเมื่อ counter เปลี่ยน

→ ตอบข้อ 4 ของใบนี้ไปในตัว: **สามก้อนที่ checkpoint อ่านไหว** เพราะไม่ต้องขออะไรเพิ่ม
รูปที่แสดงเป็นของ [ticket 06](06-checkpoint-two-buckets.md)

**4. policy warning: บรรทัดเดียว แยกตัวเลขสองแกนในนั้น**
`"...กรองออก 5 ใบ (นอกสาขา 5, ไม่ใช่สมรรถนะบัณฑิต 5)"`

ticket 12 บอกว่าตัวเลขสองแกนจะเท่ากันเกือบเสมอ ซึ่งฟังดูเหมือนเหตุผลให้ยุบเป็นตัวเลขเดียว
แต่กลับกัน: **ความเท่ากันนั้นคือข้อมูล** — วันที่สองตัวไม่เท่ากันคือวันที่สองแกนเริ่ม
แยกกันจริง และเห็นได้จากล็อกทันทีโดยไม่ต้องรัน eval. ตัวเลขรวมตัวเดียวทำให้สัญญาณนั้น
หายไปตลอดกาล

**5. ยังกรองต่อแม้เหลือต่ำกว่า `MIN_NEEDS`** — ยืนยันตาม ticket 05 ไม่เปลี่ยนเพราะ
มีสองชั้น: เติม Need นอกขอบเขตให้ครบโควตาคือการผลิต PLO ที่รู้อยู่แล้วว่าผิด
เพื่อให้ตัวเลขสวย. เฉลยมนุษย์ของ TCISM มี **4 PLO** ซึ่งต่ำกว่าพื้นอยู่แล้ว —
นั่นเป็นข้อขัดแย้งกับ immutable rule 6 ที่ **map นี้ไม่แตะ** (อยู่นอก destination)
ไม่ใช่เหตุผลให้ผ่อนการกรอง

## แก้หลังรัน pipeline เต็มครั้งแรก — กฎ any ไม่พอ

ใบนี้ตัดสินว่า **any** (สมาชิกหนึ่งคนผ่านก็พอ ต่อแกน) โดยให้เหตุผลว่า recall รายทักษะ
56% ยังไม่พอจะตัดแรง — ซึ่งถูกต้องเท่าที่ข้อมูลตอนนั้นมี **แต่พลาดตัวแปรที่ใหญ่กว่า**

`need_combination` รวมทักษะข้าม evidence เข้าเป็น Need เดียว กฎ any จึงปล่อยผ่าน
ตราบใดที่มีสมาชิกหลุดธงแค่ **ตัวเดียว** และเมื่อ Need หนึ่งมีสมาชิกหกเจ็ดตัว
เงื่อนไขนั้นแทบเป็นจริงเสมอ

**การรัน pipeline เต็มบนหลักสูตรจริงครั้งแรก** (`program-3`, evidence 14 ชิ้น,
scope statement ครบ) วัดได้ว่า:

- Need ถูกกรองเพียง **1 ใน 10** ทั้งที่มีสามใบที่เป็นกิจกรรมของสถาบันชัดเจน
- Need ที่สมาชิกติดธงนอกสาขา **6 ใน 7** และไม่ใช่สมรรถนะบัณฑิต **5 ใน 7**
  กลายเป็น **core PLO อันดับสอง** (demand 0.30) — คือ "การสร้างเครือข่ายความร่วมมือ
  ระดับนานาชาติ" ตัวอย่างต้นแบบที่ map ยกมาตั้งแต่บรรทัดแรก

**เกณฑ์ใหม่: สัดส่วน `SCOPE_PASS_RATIO = 0.5`** — ครึ่งหนึ่งของสมาชิกต้องผ่านแต่ละแกน
เลือกจากการกวาดค่าบน Need สิบใบเดียวกัน ไม่ใช่จากเลขกลม:

| threshold | กรองได้ | ควรกรองแต่รอด | กรองผิด |
|---|---|---|---|
| `> 0` (any เดิม) | 1 | **2** | 0 |
| 0.34 | 3 | 0 | 0 |
| **0.50** | **3** | **0** | **0** |
| 0.60 | 3 | 0 | 0 |
| 0.75 | 4 | 0 | **1** |

0.5 อยู่กลางช่วงที่ข้อมูลรองรับ (0.34-0.60) จึงทนต่อการเลื่อนได้มากที่สุด

**ผลข้างเคียงที่ยอมรับ**: core PLO ลดจาก 3 เหลือ 2 (ต่ำกว่า `MIN_NEEDS` มากขึ้น) —
แต่ PLO ที่หายไปคือ PLO ที่ไม่ควรมีตั้งแต่แรก ตัวเลขที่ต่ำและถูกดีกว่าตัวเลขที่ครบและผิด

**ยังเป็นหลักสูตรเดียว** — สิบ Need จากโปรแกรมเดียวปรับค่าให้เข้ากับตัวเองได้ง่าย
`scripts/eval_scope_guard.py` คือตัวที่ทบทวนค่านี้เมื่อมีคลังกว้างขึ้น
